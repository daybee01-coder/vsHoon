# DeCom 고도화2 구현 가이드

## 1. 목적과 상태

`Development.md` 12번 요구사항의 설계와 구현 기준이다. 실제 반영 범위와 검증 결과는
[DeCom 고도화2 구현 기록](additional-development-12.md)에 정리한다.

실제 D단계는 별도 Java 파서 의존성을 추가하지 않고, 주석·문자열을 마스킹한 소스 구조와 호출의 수신
클래스·인자 수·추론 가능한 인자 타입을 함께 비교하는 제한된 분석기로 구현했다. 이름만 같은 선언으로
바로 이동하지 않으며, 대상을 확정할 수 없는 오버로드는 후보로 반환한다. 지원 범위는 구현 기록에
명시한다.

목표는 디컴파일 결과를 읽기 전용 Java 문서로 제공하고, 사전 디컴파일 캐시를 문서 열기·검색·선언 이동에서 공유하는 것이다.

- 줄 번호와 현재 위치를 일반 편집기에서 표시한다.
- 클래스 안의 메서드 선언 및 같은 JAR 안의 연결된 메서드로 이동한다.
- 선택한 JAR를 백그라운드에서 미리 디컴파일하고 재실행 후에도 결과를 재사용한다.
- VSearch에서 JAR 내부 소스를 검색하고 결과의 정확한 위치로 이동한다.

읽기 전용 VFS, 원본 JAR 불변, 전체 압축 해제 없는 탐색이라는 11번의 원칙을 유지한다. 편집·재컴파일·재패키징은 범위에 포함하지 않는다. 패키징은 사용자가 직접 수행한다.

## 2. 현재 구현과 변경 지점

| 현재 파일 | 현재 역할 | 변경 방향 |
| --- | --- | --- |
| `extensions/vshoon-decom/src/archiveFileSystem.ts` | JAR entry를 읽는 VFS | 기존 탐색을 유지하고 아카이브 변경·세대 정보를 캐시와 연결 |
| `extensions/vshoon-decom/src/classEditor.ts` | 읽기 전용 Webview, 요청 시 CFR 실행, Promise 메모리 캐시 | 소스 생성·캐시를 서비스로 분리하고 일반 텍스트 편집기로 전환 |
| `extensions/vshoon-decom/src/cfr.ts` | CFR 준비 및 실행 | 취소·시간 제한·실행 수 제한을 연결 |
| `extensions/vshoon-decom/src/extension.ts` | VFS·편집기·명령 등록 | 소스 문서 제공자와 내부 연동 API 등록 |
| `extensions/vshoon-vsearch/src/types.ts` | 검색 결과·Webview 메시지 계약 | 가상 URI, 읽기 전용 결과, JAR 처리 상태 표현 |
| `extensions/vshoon-vsearch/src/searchEngine.ts` | 검색 대상 수집·검색 실행 | DeCom 검색 결과 병합 |
| `extensions/vshoon-vsearch/src/documentService.ts` | 미리보기·문서 처리 | 가상 소스 읽기와 변경 거부 |

현재 캐시는 클래스 열기 시 생성되며 영속 캐시가 아니다. VSearch의 `FileResult`에는 필수 OS 경로인 `fsPath`가 있으므로, 가상 소스를 추가하기 전에 이 전제를 사용하는 열기·미리보기·바꾸기 경로를 모두 조사한다.

## 3. 권장 구조

```text
Explorer에서 JAR 펼치기 → 기존 VFS 트리 즉시 표시
                         → 백그라운드 디컴파일 예약

클래스 열기 ──────────────┐
백그라운드 처리 ──────────┼→ 소스 서비스 → 작업 큐 → CFR
                         │      ↕
                         │   영속 캐시
                         │      ↓
                         └→ 읽기 전용 소스 문서
                                ↑
VSearch → DeCom 검색 API → URI와 위치
선언 이동 → 심볼 인덱스 → URI와 위치
```

제안 모듈은 `classSourceService.ts`, `classSourceProvider.ts`, `decompileQueue.ts`, `classSourceCache.ts`, `classSymbolIndex.ts`, `decomApi.ts`다. 실제 구현에서는 기존 유틸리티를 먼저 재사용하고 필요할 때만 파일을 나눈다.

제품 로직은 기존 built-in extension 안에서 우선 해결한다. 클래스 클릭을 일반 문서 열기로 연결할 수 있는지 기존 Explorer seam과 확장 등록을 먼저 조사한다. 코어 변경이 필요하면 최소한으로 제한하고 같은 변경에서 패치 저장, 패치 장부, 관련 테스트를 갱신한다.

## 4. 읽기 전용 소스 문서와 줄 번호

### 문서 모델

- 원본 바이트는 기존 `vshoon-jar:` URI로 읽는다.
- 디컴파일 결과는 별도 스킴(제안: `vshoon-decom:`)으로 제공한다. `.class` 바이트와 Java 텍스트의 URI를 구분한다.
- 우선 `TextDocumentContentProvider` 기반 읽기 전용 문서를 검토하고, 일반 편집기로 열어 Java 언어 모드를 설정한다.
- 가상 URI에서 원본 JAR, 중첩 JAR 경로, 클래스 entry를 손실 없이 복원할 수 있게 한다. 문자열 구분자 조합 대신 공용 URI 생성·해석 함수를 사용한다.
- 탭에는 클래스 이름, 설명에는 원본 JAR 경로를 표시한다. 같은 이름의 클래스도 JAR가 다르면 별도 문서다.
- 내부 클래스는 별도 문서로 두지 않는다. CFR가 outer/inner 묶음을 한 텍스트로 만들므로 `Foo$Bar.class`는 `Foo`의 문서를 연다. 묶음당 디컴파일러 실행은 한 번이다.
- 줄 번호는 기존 편집기 설정을 존중한다. 총 줄 수 표시가 별도로 필요하면 소스 문서 상태 정보에 추가한다.

줄 번호는 디컴파일 결과의 번호이며 원본 Java 파일의 번호가 아니다. 설명 배너를 소스 텍스트 앞에 삽입하여 검색·이동 좌표가 달라지지 않도록 한다. 모든 좌표는 같은 캐시 텍스트에서 계산하고 내부적으로 0-based 줄·UTF-16 열 인덱스를 사용한다.

### 기존 동작 전환

Explorer 클릭, `decom.viewClassFile`, 로컬 `.class` 열기, 검색 결과 열기가 공통 소스 열기 경로를 사용하도록 한다. 기존 custom editor 등록과 충돌하거나 바이너리 편집기가 먼저 열리지 않는지 확인한다. 기존 명령은 호환성을 유지하고 신규 설정·명령은 `vshoon.*` 접두사를 사용한다.

## 5. 사전 디컴파일과 캐시

### 시작 조건과 범위

- 사용자가 JAR를 처음 펼치면 트리를 먼저 표시하고 해당 JAR의 클래스 처리를 예약한다.
- 기본 대상은 사용자가 연 JAR다. 워크스페이스의 모든 JAR를 시작 시 자동 처리하지 않는다.
- 중첩 JAR는 기본적으로 해당 노드를 펼쳤을 때 처리한다. 명시적 전체 분석 명령에서는 중첩 포함을 선택할 수 있게 한다.
- 사용자가 직접 연 클래스는 대기열의 최우선으로 승격한다. 사전 처리가 끝나지 않았으면 진행 상태를 표시한다.
- CFR나 Java 실행 환경을 준비하지 못하면 백그라운드 처리를 실패 상태로 정리하고 원인과 재시도 방법을 표시한다. 요청마다 알림을 반복하지 않는다.

### 작업 큐

초기 동시 실행 수는 1로 시작하고 측정 후 조정한다. 사용자 요청과 사전 처리 요청은 동일 캐시 키의 작업을 공유한다. 한 소비자의 취소로 다른 소비자가 기다리는 작업을 종료하지 않도록 참조 수나 별도 구독 수명을 관리한다.

작업별 시간 제한, 취소, 프로세스 종료, 임시 입력 정리를 보장한다. 원본 변경·캐시 삭제 시 세대를 바꾸고 이전 작업이 뒤늦게 결과를 게시하지 못하게 한다. 전체 JAR를 한꺼번에 추출하지 않고 현재 outer/inner 클래스 묶음 처리를 재사용한다. 클래스마다 JVM을 실행하는 비용을 측정한 후에만 제한된 배치 실행 등을 검토한다.

### 저장과 무효화

영속 캐시는 확장 전용 저장소에 두고 워크스페이스에 `.java` 파일을 생성하지 않는다. 저장 항목은 소스 텍스트, 원본 식별 정보, 캐시 형식 버전, 생성 도구 정보, 크기 및 마지막 사용 시각이다.

캐시 유효성에는 다음 정보가 필요하다.

- 원본 JAR의 정규화된 URI와 내용 지문
- 중첩 JAR의 전체 entry 체인과 클래스 묶음 식별 정보
- CFR 버전 또는 사용자 지정 CFR 파일의 내용 지문
- 디컴파일 옵션, 결과에 영향을 주는 실행 환경·추가 classpath 내용 지문
- 캐시 스키마 버전

mtime·크기는 빠른 변경 감지에만 사용한다. 재시작 후 동일 크기·동일 시각으로 교체된 JAR까지 판별하려면 비동기 스트리밍 해시 등 내용 검증이 필요하다. 검증 때문에 Explorer 표시를 막지 않는다. 검증 전 캐시는 검색의 확정 결과로 취급하지 않는다.

소스 파일은 임시 파일에 완전히 기록한 뒤 교체하고 메타데이터를 게시한다. 손상되거나 불완전한 항목은 다시 생성한다. 여러 창이 같은 캐시를 사용하므로 고유 임시 이름과 게시·삭제 경합 처리가 필요하다. 용량 상한과 오래 사용하지 않은 항목부터 정리하는 정책을 제공하고, 열린 문서·진행 작업의 데이터를 삭제해 동작을 깨뜨리지 않는다.

원본 변경 시 해당 JAR의 캐시·검색 상태·심볼 인덱스를 함께 무효화하고 열린 문서 갱신을 알린다. 실패는 성공 캐시로 저장하지 않고 현재 실행에서 반복 재시도만 억제한다.

## 6. VSearch 연동 계약

### 소유권

DeCom이 캐시를 소유하고 VSearch는 버전이 있는 확장 export API를 통해 소스 검색·읽기를 요청한다. VSearch에서 캐시 디렉터리 구조나 다른 확장의 저장 키를 직접 읽지 않는다. API가 없거나 지원 버전이 아니면 일반 파일 검색을 계속 제공한다.

초기 API 계약에는 다음 동작을 포함한다. 정확한 TypeScript 타입은 구현 전 양쪽 확장에서 합의한다.

| 동작 | 입력 | 출력 |
| --- | --- | --- |
| 기능 확인 | 지원 API 버전 | 검색·소스 읽기 지원 여부 |
| 검색 | 범위, 검색 옵션, 제한, 취소 토큰 | 제한된 크기의 결과 배치와 완료 상태 |
| 소스 읽기 | 검증된 소스 URI | 텍스트와 소스 버전 |
| 분석 요청 | 대상 JAR, 중첩 포함 여부 | 작업 식별자·처리 상태 |

검색 결과는 소스 URI, 원본 표시 경로, 줄·열·길이, 미리보기, 소스 버전, `readonly: true`를 가진다. 완료 상태는 준비된 클래스 수, 전체 대상 수, 실패 수, 취소·제한 초과·미완료 여부를 구분한다. 결과 수와 배치 크기를 제한해 확장 호스트에 전체 소스를 한 번에 전달하지 않는다.

### 검색 규칙

- `JAR 내부 포함` 옵션은 초기 기본값을 끔으로 제안한다. 켜면 선택한 검색 범위에 속한 JAR를 대상으로 한다.
- 아직 열지 않은 JAR도 옵션을 켠 검색 범위에서는 발견하고 분석 예약할 수 있다. 검색과 분석 모두 취소·대상 수 제한을 적용한다.
- 워크스페이스·지정 디렉터리·하위 폴더 옵션과 제외 규칙을 외부 JAR 경로에 먼저 적용한다.
- 클래스 파일 마스크는 논리적 `.class` entry 경로를 기준으로 적용한다. `*.java`로도 디컴파일 소스를 포함할지는 UI 설명과 함께 후속 결정한다.
- 대소문자·단어 단위·정규식은 일반 검색과 같은 의미를 갖도록 기존 matcher를 재사용하거나 계약 테스트로 동등성을 검증한다.
- 처리된 소스에서 결과를 먼저 반환하고 미완료 상태를 표시한다. 전체 분석이 끝나지 않았으면 결과가 없다는 이유로 JAR 전체에 일치 항목이 없다고 단정하지 않는다.
- 첫 구현은 자동 결과 재배열 대신 `분석 완료 후 다시 검색`을 제공한다.
- 결과 표시는 `app.jar!/BOOT-INF/lib/lib.jar!/com/example/App.class`처럼 원본 계층을 유지한다.
- 클릭 시 동일 소스 버전의 위치로 이동한다. 원본이 바뀌었으면 최신 문서를 열고 검색 갱신을 안내해 오래된 좌표를 사용하지 않는다.

`FileResult`는 일반 파일과 JAR 소스를 구분하는 타입으로 확장하는 것을 권장한다. 가상 결과에 가짜 `fsPath`를 넣지 않는다. 미리보기는 읽기 전용으로 표시하고, 단일 바꾸기·전체 바꾸기·미리보기 저장은 UI와 확장 호스트 양쪽에서 JAR 소스를 제외 또는 거부한다.

## 7. 메서드 선언 이동

### 단계별 범위

1. 현재 클래스의 메서드 목록과 선언 위치를 제공한다.
2. 현재 클래스 내부 호출에서 선언으로 이동한다.
3. 같은 JAR의 다른 클래스와 메서드로 이동한다.
4. 중첩 JAR·외부 의존성·상속 관계는 후속 단계로 확장한다.

메서드 이름만 정규식으로 찾는 구현을 정확한 선언 이동으로 제공하지 않는다. 오버로드, 생성자, 중첩 클래스, 상속, 변수 타입을 구분해야 한다.

심볼 식별자는 JAR 식별자, 클래스 전체 이름, 메서드 이름, JVM descriptor를 기준으로 설계하고 소스 버전별 선언 범위를 별도로 저장한다. 단, 바이트코드의 호출 대상 정보만으로 디컴파일 텍스트의 클릭 위치가 자동 연결되지는 않는다. Java 구문 분석과 호출 위치 매핑이 필요하다.

구현 첫 단계에서 Java 언어 서비스가 해당 가상 문서와 classpath를 실제로 지원하는지 작은 실험으로 검증한다. 지원되지 않으면 자체 구문 분석을 사용하는 제한된 탐색으로 시작한다. 새로운 파서 의존성을 도입할 때는 라이선스, 배포 크기, 오류 복구 능력을 확인한다.

대상을 확정할 수 있을 때만 직접 이동한다. 불명확하면 후보 목록을 표시하고, 의존성이 없으면 찾지 못한 이유를 알린다. 실제 실행 시의 동적 호출 대상 전체를 찾는 기능과 선언 이동을 구분한다. 처음부터 사용처 검색이나 완전한 Java 분석을 완료 조건에 넣지 않는다.

## 8. UX와 수명주기

- 분석 상태는 `대기`, `진행`, `완료`, `일부 실패`, `취소`로 구분한다.
- 트리 탐색과 클래스 직접 열기는 백그라운드 분석 완료를 기다리지 않는다.
- 분석 취소·재시도·캐시 삭제를 명령으로 제공한다.
- 신규 사용자 문자열은 기존 현지화 체계를 사용한다.
- 키보드로 검색 결과 선택, 문서 열기, 선언 이동, 뒤로 가기를 사용할 수 있게 한다.
- 파일 감시, 작업 큐, 이벤트 구독과 프로세스는 명확한 소유자에 등록하고 확장 종료 시 정리한다.
- Remote URI를 로컬 OS 경로로 변환하지 않는다. 초기 지원은 기존 로컬 JAR 범위로 명시하고 미지원 URI에는 이유를 표시한다.
- 기존 ZIP entry 경로 검증·크기 제한을 유지하고 백그라운드 처리에도 작업량·임시 파일·캐시 상한을 적용한다.

## 9. 구현 순서와 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| A | 소스 서비스 분리, 일반 읽기 전용 편집기 | 로컬·JAR·중첩 클래스 열기, 줄 번호·검색·복사, 원본 불변 |
| B | 영속 캐시와 백그라운드 큐 | 재시작 재사용, 직접 열기 우선, 취소·실패 복구·변경 무효화 |
| C | VSearch API와 결과 통합 | 범위·옵션 일치, 미완료 상태, 위치 이동, 모든 쓰기 경로 차단 |
| D | 심볼 인덱스와 선언 이동 | 현재 클래스부터 같은 JAR까지 검증된 범위 제공, 모호한 대상 후보 표시 |

각 단계는 독립적으로 검토 가능한 변경으로 만든다. 문서에는 구현한 범위와 미지원 범위를 구분해서 기록한다.

## 10. 검증 계획

### 자동 검증

- URI: 공백·한글·`!`·`#`·중첩 경로 왕복, 동일 클래스명 충돌 방지.
- 캐시: 재시작 재사용, 동일 크기·시각의 내용 교체, CFR·옵션 변경, 손상된 캐시 복구.
- 경합: 동일 클래스 요청 병합, 사용자 요청 승격, 한 소비자 취소, 삭제·원본 변경 후 늦은 결과 차단, 여러 창의 게시 경합.
- 자원: 시간 초과·CFR 실패 후 프로세스와 임시 파일 정리, 용량 제한.
- 검색: 일반 파일과 JAR 혼합, 범위·제외·정규식·한글·UTF-16 좌표, 결과 제한·취소·미완료 상태.
- 읽기 전용: 단일 바꾸기·전체 바꾸기·미리보기 저장의 호스트 측 거부.
- 탐색: 오버로드·생성자·inner class·다른 JAR의 같은 클래스명·누락 의존성·모호한 호출.
- 실제 CFR fixture: 단순 클래스, outer/inner 묶음, 중첩 JAR에서 생성 텍스트와 이동 범위 확인.

저장소 루트의 `npm run test:decom`과 관련 VSearch 테스트를 우선 사용한다. 실제 CFR 테스트에 필요한 환경은 기존 테스트 스크립트를 확인한다. 타입·린트 검사는 변경 범위에 맞게 실행하고 코어 변경 시 패치 검사와 Explorer 회귀 테스트를 추가한다.

### 수동 검증과 성능

데스크톱 실행 전 루트에서 `npm run build`를 실행한다. 작은 JAR, 클래스가 많은 JAR, 중첩 JAR를 사용하여 다음을 측정한다.

- 캐시가 없을 때 트리 표시 시간과 첫 클래스 표시 시간
- 캐시가 있을 때 클래스 표시 시간과 재시작 후 재사용
- 백그라운드 처리 중 CPU·메모리·디스크 사용량과 편집기 반응
- 사용자 직접 열기 요청의 대기 시간
- 검색 시작부터 첫 결과·완료까지의 시간

변경 전 기준값을 기록하고 같은 환경·같은 입력으로 비교한다. 수치 목표는 기준 측정 후 정하며, 측정 없이 성능 개선을 완료로 표시하지 않는다. 기본 Workbench 실행과 키보드 탐색도 확인한다. 검증 결과는 후속 구현 기록에 실제 실행한 명령·결과·제약과 함께 남긴다.
