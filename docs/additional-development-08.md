# 추가 개발 8 — 새 프로젝트 창과 JAR 소스 탐색

> 이 문서의 "JAR 소스 탐색" 부분은 [추가 개발 9](additional-development-09.md)가 대체한다. 열 때 JAR
> 전체를 디컴파일해 `.java` 스냅샷을 보여주는 동작은 없앴다. 새 프로젝트 창(VSH-0015) 부분은 유효하다.

## 동작

- 새 시작 창에서 폴더, 워크스페이스, 최근 프로젝트를 선택하면 새 IDE 창을 연다. 같은 프로젝트가 이미 열려 있어도 별도 창으로 연다. 일반 CLI 실행의 중복 처리 정책은 유지한다.
- 실제로 선택한 Workbench가 준비된 뒤 시작 창을 닫는다. 창 열기가 취소되거나 실패하면 시작 창으로 돌아온다.
- JAR 더블클릭 또는 `Decom: JAR 파일 열기`는 원본 파일을 추출하고 CFR로 전체 JAR의 Java 소스를 미리 만든다. 탐색기에 원본 파일 폴더와 `Java 소스 (읽기 전용)` 폴더가 나타난다.
- 소스 폴더는 기본 탐색기와 텍스트 편집기를 사용하므로 패키지 탐색, 파일 열기, 텍스트 찾기를 사용할 수 있다. 내부 클래스는 CFR이 외부 클래스 소스에 합친다. 중첩 JAR는 원본 폴더에서 다시 열 수 있다.
- 같은 JAR의 반복 열기는 캐시를 재사용한다. 새로고침은 새로운 소스 스냅샷으로 교체하고, 마운트 해제는 원본과 소스 폴더를 함께 제거한다. 진행률 알림에서 디컴파일을 취소할 수 있다.
- Java/CFR를 실행할 수 없으면 경고 후 원본 파일 폴더를 제공한다. 기존 `.class` 뷰어도 유지한다.

## JAR 저장 기능의 범위

기존 기능은 `javac`로 Java를 컴파일하는 기능이 아니라 원본 바이트와 편집한 리소스·교체한 클래스·중첩 라이브러리를 JAR로 다시 묶는 기능이다. 해당 명령, 최초 백업, 취소 시 원본 보존, 중첩 JAR의 무압축 저장을 유지한다.

생성한 Java 소스는 `.decom/sources-*` 스냅샷에 보관하고 읽기 전용 파일 시스템으로 노출한다. `.decom`은 기존 재빌드 제외 경로이므로 생성한 Java가 JAR에 섞이지 않는다. 저장 후 다음 열기에서 소스를 다시 준비한다. 기존에 열린 소스 탭은 이전 스냅샷을 계속 읽을 수 있다.

## 검증

모두 Windows 개발 빌드에서 실행했다. 패키징은 실행하지 않았다.

| 항목 | 명령 | 결과 |
| --- | --- | --- |
| 코어 타입 검사 | `npm run typecheck` | 통과 |
| VShoon 소스 린트 | `npm run lint` | 통과 |
| Decom 확장 컴파일·단위 테스트 | `npm run test:decom` | 25개 통과 (`VSHOON_TEST_CFR_PATH`를 지정해 실제 CFR 경로까지 포함) |
| 시작 창 데스크톱 스모크 | `npm run smoke:start-window` | 통과 (아래 정정 참고) |
| Decom 데스크톱 스모크 | `npm run smoke:decom` | 연속 2회 통과 (1회 약 3분 30초) |

`npm run layers`는 `src/vs/vshoon/browser/fileDialog/vshoonFileDialog.ts`의 `INativeEnvironmentService` 참조를
보고한다. 이번 변경과 무관한 기존 위반이라 그대로 두었다.

### 검증에서 찾아 고친 것

1. **확정되지 않은 워크스페이스 갱신에 묻히던 마운트.** 확장 호스트는 앞선
   `updateWorkspaceFolders`를 창이 확인하기 전까지 다음 호출을 `false`로 거절한다. 열기·새로고침·마운트
   해제가 모두 폴더 목록을 교체하므로, 바로 이어지는 동작이 조용히 아무 일도 하지 않았다. 새로고침은
   옛 소스 스냅샷을 그대로 두었고 마운트 해제는 반환값을 아예 보지 않았다. 이제 `setWorkspaceFolders`가
   목록이 실제로 일치할 때까지 재시도하고, 실패하면 마운트 해제도 오류를 알린다. 단위 테스트
   `a folder update the window has not confirmed yet is retried, not dropped`가 이 경로를 고정한다.
2. **단일 폴더 워크스페이스에서의 마운트.** 폴더가 하나뿐인 창에 폴더를 추가하면 VS Code가 untitled
   워크스페이스로 전환하고, 그 전환이 확인되기 전까지 이후 폴더 갱신이 모두 거절된다. Decom 스모크는
   그래서 다중 루트 `.code-workspace`를 열어 새로고침과 마운트 해제를 일반적인 폴더 갱신으로 검증한다.
3. **시작 창 스모크의 불안정한 단정 세 가지.** 빈 창 제목을 시작 시점 값과 비교하던 단정은 Welcome
   편집기가 열리며 제목이 바뀌어 실패했다. 이제 프로젝트 이름이 그 창에 나타나지 않는지를 본다. 개발
   빌드의 두 번째 인스턴스는 인자를 넘기기까지 3~27초가 걸리고 그 뒤에도 살아남는 일이 잦아, 런처
   프로세스의 종료가 아니라 요청이 만든 창을 기다리도록 바꿨다. 시작 창 렌더러의 최근 항목 대기도
   10초에서 30초로 늘렸다.
4. **Decom 스모크를 굶기던 채팅 에이전트.** 토큰 없이 GitHub 재시도를 반복하며 확장 호스트를 응답
   불능으로 만들었다. 스모크 프로필에서 `chat.disableAIFeatures`로 껐다.
5. **정리 실패가 통과한 실행을 실패로 만들던 문제.** Windows에서 Electron 보조 프로세스가 프로필을
   잡고 있으면 삭제가 EPERM으로 끝난다. 시작 창 스모크와 같이 경고만 남기도록 했다.

### 정정 — 시작 창 스모크의 CLI 단계

위 표의 "연속 4회 통과"는 그 시점의 관찰이었고, 이후 같은 테스트가 절반 가까이 실패했다. 원인은 이
저장소의 변경이 아니라 개발 빌드의 두 번째 인스턴스 처리다. `vs Hoon.exe <폴더> --new-window`로 실행한
런처 프로세스가 실행 중인 인스턴스에 인자를 넘기지 못한 채 멈추고, 창이 아예 생기지 않는다. 실행할
때마다 재현되지는 않지만, 이 스모크가 띄운 인스턴스를 상대로는 첫 시도가 거의 매번 실패했다. CLI는
`vshoonNewProjectWindow`를 전달하지 않으므로 VSH-0015와 무관하며, 시작 창을 쓰지 않는 인스턴스에서도
재현된다.

그래서 스모크에서 이 경로를 없앴다. 이제 두 단계로 돈다. 1단계는 폴더 없이 띄워 런처 접근성, 빈 창
전환, Workbench의 새 창 동작, contribution health를 확인한다. 2단계는 그 인스턴스를 끄고 프로젝트
폴더를 인자로 새로 띄워 — 명시적 대상이 런처를 건너뛰는 것도 함께 확인된다 — 런처에서 같은 프로젝트를
골랐을 때 별도 창이 생기는지 본다. 재구성 후 6회 연속 통과했다.

### 하지 않은 것

- 패키지 빌드와 패키징 후 스모크는 실행하지 않았다.
- 대형 JAR, 손상된 JAR, 긴 Windows 경로, 중첩 JAR 재열기, Java/CFR가 없는 환경의 경고 경로는 수동으로도
  확인하지 않았다.
- 옛 소스 스냅샷은 새로고침 후에도 `.decom` 아래에 남는다. `.decom`은 재빌드 제외 경로라 JAR에는 섞이지
  않지만 디스크에는 쌓인다.
