# 성능 개선 7차: JAR 압축·해제의 워커 격리와 진행률·취소

작성일: 2026-09-09. 대상: [성능 개선 가이드](performance-improvement-guide.md)의 P1-C.

## 이어받은 상태와 범위

- 작업 시작 시 HEAD는 `2ec7fa0`이고 작업 트리에는 6차 변경이 아직 커밋되지 않은 채로 있었다. 이번 차수는 그 위에 이어서 작업했다.
- 검증에는 기존 `.build/tools/node-v24.18.0`을 명령별 PATH로 사용했다. 시스템 Node·사용자 프로필·캐시는 변경하지 않았다.
- 6차에서 마련한 데이터 보존 기준선(왕복 테스트, 임시 파일 교체, 엔트리 경로 경계) 위에 구조 변경을 얹었다. 가이드 구현 순서 3번이 요구한 선행 조건이 이번 변경의 전제다.
- P0 배포판 A/B 측정, P1-B 대화상자 실사용 검증, P2-A/P2-B의 남은 측정, P2-C, P2-D의 이전 로직은 이번 범위 밖이다.

## 변경

### 1. 압축·해제를 워커 스레드로 옮겼다

`adm-zip`의 읽기·쓰기·압축은 전부 동기다. 지금까지는 `extractAllEntries`와 `rebuildJarFromFolder`가 확장 호스트에서 직접 돌았고, 그동안 같은 호스트의 다른 확장은 통째로 멈췄다.

같은 저장소의 VSearch가 쓰는 방식과 같은 모양으로 [jarWorker.ts](../extensions/vshoon-decom/src/jarWorker.ts)를 두고, 호스트 쪽은 [jarWorkerClient.ts](../extensions/vshoon-decom/src/jarWorkerClient.ts)가 워커를 띄워 결과를 받는다. 주고받는 값의 타입은 [jarWorkerProtocol.ts](../extensions/vshoon-decom/src/jarWorkerProtocol.ts)에 모았다 — `vscode`도 `adm-zip`도 참조하지 않으므로, 호스트가 타입을 쓰는 것만으로 압축 라이브러리를 로드하지는 않는다.

- `zipUtil.ts`의 두 함수는 여전히 동기이며 계산 내용도 그대로다. 달라진 것은 호출되는 위치와, 진행률·취소 콜백을 받는다는 점뿐이다. 6차의 왕복 보존 테스트가 그대로 통과하는 것으로 동작이 바뀌지 않았음을 본다.
- 클라이언트는 `vscode`를 참조하지 않는다. 취소는 `vscode.CancellationToken`이 구조적으로 만족하는 최소 형태(`CancellationLike`)로만 받으므로, 확장 호스트를 띄우지 않고 이 경로를 테스트할 수 있다.

### 2. 취소를 공유 메모리 플래그로 전한다

워커가 동기 루프를 도는 동안에는 `postMessage`가 워커에 도달하지 못한다. 이벤트 루프가 비어야 메시지를 처리하는데, 그 루프를 압축이 잡고 있기 때문이다. 그래서 취소는 `SharedArrayBuffer` 한 칸을 `Atomics`로 읽어 항목 사이에서 확인한다.

- 확인 간격은 50개 항목마다다. 항목 하나하나마다 확인/보고하면 그 자체가 비용이다.
- 압축(`toBuffer()`)은 한 덩어리라 중간에 끊을 수 없다. 대신 압축이 끝난 직후 한 번 더 확인해서, **원본 자리로 옮기기 전에** 멈춘다. 취소한 사용자는 원본 jar가 바뀌는 것을 보지 않는다.
- 그래도 끝나지 않으면 호스트가 5초 뒤 워커를 강제로 내린다. 그 경우 남았을 수 있는 `.decom-tmp`는 호스트가 지운다.

### 3. 진행률을 보여주고 취소 버튼을 붙였다

`decom.openJar`·`decom.refreshJar`·`decom.saveToJar`가 `cancellable: true`인 진행률 알림을 띄운다. 추출은 `n/전체개수 항목`, 저장은 수집 개수 → `압축 중...` → `파일 쓰는 중...`으로 단계가 바뀐다.

진행률 메시지는 워커에서 100ms 간격으로 줄여 보낸다. 개수 기준으로만 보내면 작은 항목이 많은 jar에서 메시지가 몰려, 정작 막지 않으려던 호스트의 이벤트 루프를 다시 채우게 된다. 단계가 바뀌는 순간은 사용자가 봐야 하므로 간격과 무관하게 내보낸다.

### 4. 반쪽 캐시가 유효한 것으로 재사용되지 않게 했다

추출을 취소하면 이미 풀어낸 파일은 캐시 폴더에 남는다. 그대로 두면 다음에 같은 jar를 열 때 매니페스트의 크기·수정시각이 일치해 **반쪽짜리 캐시를 원본과 같은 것으로 재사용**한다.

매니페스트에 `incomplete` 필드를 두고, 추출을 시작하기 전에 `true`로 써 둔 뒤 끝나야 `false`로 바꾼다. 열 때 `incomplete`이면 되묻지 않고 바로 다시 추출한다 — 사용자에게 물어도 고를 것이 없기 때문이다. 필드는 선택적이라 이전 버전이 쓴 매니페스트도 그대로 읽힌다. 백업 경로(`backupPath`)는 이 과정에서 유지된다.

## 측정

3,000개 항목(항목당 20KB)짜리 JAR을 임시 폴더에 만들어, 16ms 간격 타이머의 실제 지연으로 **호출한 쪽 프로세스가 멈춘 시간**을 쟀다. 3회 반복이며 값은 각 회차의 최댓값이다.

| 작업 | 확장 호스트에서 직접(변경 전) | 워커(변경 후) |
| --- | --- | --- |
| 추출 | 6,875 / 6,881 / 7,623 ms | 36 / 100 / 178 ms |
| 저장 | 2,151 / 2,309 / 2,329 ms | 33 / 54 / 71 ms |

- **개선된 것은 호출한 쪽이 멈추는 시간뿐이다.** 벽시계 시간(작업 전체가 끝나기까지)은 추출 1.9~7.3초, 저장 2.3~2.9초로 측정 회차 간 산포가 두 방향 차이보다 커서, 이 측정으로는 빨라졌다고도 느려졌다고도 말할 수 없다. 워커 시작 비용(아래)만큼은 늘어나는 것이 맞다.
- 워커 경로에도 33~178ms의 정지가 남는다. 항목 1개짜리 jar로 잰 워커 시작 비용은 벽시계 43~56ms, 호출한 쪽 정지 9~19ms였다. 나머지가 진행률 처리인지 디스크 경합인지는 분리해 측정하지 않았다.
- 이 측정은 확장 호스트가 아니라 **일반 Node 프로세스**에서 같은 모듈을 호출한 것이다. 실제 VS Code 확장 호스트에서 다른 확장의 응답이 얼마나 좋아지는지는 측정하지 않았다.
- 측정에 쓴 스크립트는 임시 폴더에서만 돌렸고 저장소에 남기지 않았다. 실제 사용자 JAR·워크스페이스에는 접근하지 않았다.

측정 조건: 2026-09-09, Windows 11, `.build/tools/node-v24.18.0`, 임시 폴더의 합성 JAR(0.5MB, 3,000개 항목). 전원 모드·백그라운드 부하는 통제하지 않았다.

- 진행 중 고친 것: 처음 만든 측정 스크립트는 이벤트 루프 지연을 항상 0ms로 보고했다. 막혀 있던 타이머가 실제로 한 번 뛰기 전에 측정을 끝냈기 때문이며, 측정 뒤 한 틱을 기다리도록 고쳤다. 위 표는 고친 뒤의 값이다.

이번에 추가한 테스트:

1. [jarWorkerClient.test.ts](../extensions/vshoon-decom/src/jarWorkerClient.test.ts) — 워커를 실제로 띄워 추출 결과가 항목·바이트 그대로인지, 진행률이 보고되는지, 왕복 후 편집 내용이 반영되고 중첩 jar가 남는지 확인한다.
2. 없는 jar는 오류로 돌아오고, 이미 취소된 토큰이면 워커를 띄우지 않고 끝난다.

**워커를 실제로 돌리는 중간에 취소하는 경로는 자동 테스트로 덮지 않았다.** 그 시점을 테스트에서 정확히 맞출 수 없어 결과가 실행마다 달라지기 때문이다. 대신 취소 판정 자체는 `zipUtil`의 동기 경로에서 결정적으로 검증하고, 워커 경로에서는 시작 전 취소와 임시 파일 정리를 검증한다.

## 하지 않은 것

- **메모리는 줄지 않았다.** `toBuffer()`가 zip 전체를 한 버퍼에 담고, 재빌드가 모든 파일 내용을 메모리에 올려 두는 성질은 그대로다. 달라진 것은 그 메모리를 쓰는 곳이 확장 호스트가 아니라 워커라는 점뿐이다. 실제로 낮추려면 스트리밍 zip 작성기가 필요하고, 그것은 압축 라이브러리를 바꾸는 별도 작업이다. 최대 메모리도 측정하지 않았다.
- 파일 I/O 동시성은 제한하지 않았다. 워커 안에서는 여전히 동기라 한 번에 하나씩 처리된다.
- 실제 대형 JAR, 손상된 JAR, 긴 Windows 경로, `.class` 디컴파일(CFR) 경로, 진행률·취소 UI의 실제 조작은 확인하지 않았다. 제품 코어를 수정하지 않아 코어 빌드/layers/patch 저장도 실행하지 않았다. 패키징·커밋·원격 push는 하지 않았다.
