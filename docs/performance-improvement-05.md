# 성능 개선 5차: 쿼리 보관 목록의 순차 stat 제거

작성일: 2026-09-09. 대상: [성능 개선 가이드](performance-improvement-guide.md)의 P2-D 중 목록 조회.

## 이어받은 상태와 범위

- 작업 시작 시 HEAD는 `6c6721d`이며, 작업 트리에는 [2차](performance-improvement-02.md)·[3차](performance-improvement-03.md)·[4차](performance-improvement-04.md) 변경이 커밋되지 않은 채 남아 있었다. 모두 그대로 보존했다.
- 검증에는 기존 `.build/tools/node-v24.18.0`을 명령별 PATH로 사용했다. 시스템 Node·사용자 프로필·캐시는 변경하지 않았다.
- P0 배포판 A/B 측정, P1-B 대화상자 실사용 검증, P1-C JAR worker 격리는 여전히 남아 있다. 이번에는 그 항목들과 독립적으로 검증할 수 있는 P2-D의 목록 조회만 다뤘다.
- P2-D의 다른 절반인 `migrateLegacy()`(활성화마다 예전 폴더 검사, 완료 표시 없음)는 **손대지 않았다.** 원본 보존과 재시도 조건이 걸린 데이터 이전이라 목록 조회와 같은 변경으로 묶지 않는다.

## 변경

[queryStore.ts](../extensions/vshoon-dbconn/src/features/queryStore.ts)의 `list()`는 폴더를 한 번 열거한 뒤 SQL 파일마다 `vscode.workspace.fs.stat`을 `await`로 하나씩 기다렸다. 파일이 n개면 조회 왕복이 n번 직렬로 이어진다. 열거 결과에는 수정 시각·크기가 없으므로 `stat` 자체는 없앨 수 없다.

- 걸러내기·동시성·정렬 규칙을 [queryList.ts](../extensions/vshoon-dbconn/src/features/queryList.ts)로 분리했다. 이 모듈은 `vscode`를 참조하지 않고 열거·조회 두 동작만 넘겨받는다. 확장 호스트를 띄우지 않고도 동시 조회 수와 목록 순서를 테스트할 수 있게 하려는 것이며, 이 확장의 다른 순수 로직 모듈(`queryFiles.ts`, `scriptIndex.ts`)과 같은 구성이다.
- 표시 결과는 그대로다. 폴더와 SQL 아닌 파일 제외(대소문자 무시), 조회 실패 항목 제외, 최신 수정순 정렬이 모두 이전과 같다. 실패 한 건이 목록 전체를 실패로 만들지 않는 동작도 유지했다.
- 동시 조회 한도 `QUERY_STAT_CONCURRENCY = 8`은 **측정으로 정한 최적값이 아니다.** 순차 대기를 없애면서 파일이 많은 폴더에서 조회를 무제한으로 열지 않기 위한 값이다. 가이드의 "SQL 파일이 많은 조건에서 목록 갱신을 측정한다"는 아직 미충족이다.
- 총 `stat` 호출 수는 줄지 않는다. 줄어드는 것은 직렬 대기다. 파일이 한도 이하인 폴더에서는 이전과 차이가 거의 없다.
- 결과를 입력 순서대로 돌려주므로 수정 시각이 같은 파일들의 상대 순서가 조회 완료 순서에 흔들리지 않는다. 이전 순차 코드도 열거 순서였고, 그 성질을 유지했다.

동시성 헬퍼는 새 클래스를 만들지 않고 이 확장이 이미 쓰는 [util/async.ts](../extensions/vshoon-dbconn/src/util/async.ts)에 `mapWithLimit`으로 추가했다. 4차에서 만든 VSsh의 `AsyncSemaphore`는 다른 확장 패키지에 있어 import할 수 없다.

목록 캐시는 도입하지 않았다. 가이드가 요구한 "명확한 무효화 조건"이 없는 상태에서 캐시를 넣으면 외부에서 폴더를 바꿨을 때 목록이 틀리게 된다.

## 검증 결과

- `npm run test:dbconn`: 컴파일 오류 0, 테스트 348개 전부 통과(신규 6개 포함). 기존 342개의 결과 변화 없음.
- `npm run core -- exec -- eslint <변경·신규 파일 4개>`: 신규 파일 2개 오류·경고 0.
- 첫 컴파일에서 `noUncheckedIndexedAccess`로 인한 인덱스 접근 타입 오류를 발견해, 캐스트 없이 작업 큐를 꺼내 쓰는 형태로 바꿨다. 첫 린트에서는 신규 파일의 저작권 헤더 누락을 발견해 추가했다. 이 확장의 **기존** 파일들(`queryStore.ts`, `util/async.ts` 등)에 남아 있는 헤더 위반과 `async.ts`의 미사용 eslint-disable 경고는 이번 범위 밖이라 그대로 뒀다.
- `git diff --check` 통과.

새 테스트([queryList.test.ts](../extensions/vshoon-dbconn/src/features/queryList.test.ts))가 검증하는 내용:

1. SQL 파일 50개 폴더에서 `stat` 호출은 50회 그대로이고 동시 실행 최고치는 8. 목록의 처음·끝 항목과 개수가 최신순과 일치. 이전 코드였다면 최고치가 1이 되는 입력이다.
2. 조회가 실패한 파일만 빠지고 나머지 목록은 유지된다.
3. 폴더·SQL 아닌 파일은 `stat`을 호출하지도 않는다.
4. 수정 시각이 같은 항목들은 조회가 늦게 끝나도 폴더 열거 순서를 유지한다.
5. 빈 폴더, 그리고 한도가 0처럼 잘못된 값일 때(최소 1로 처리) 목록이 정상적으로 만들어진다.

가짜 폴더만 사용했고 실제 사용자 SQL 파일·DB 연결에는 접근하지 않았다. 실제 보관 폴더에서의 목록 갱신 지연 측정, `기존 쿼리 열기` 명령의 실사용 확인, 삭제 후 목록 재조회 UI 흐름은 이번 단계에서 수행하지 않았다. 제품 코어를 수정하지 않아 코어 빌드/layers/patch 저장도 실행하지 않았다. 패키징·커밋·원격 push는 하지 않았다.

## 남은 작업

1. P0: 동일 빌드 ZIP/설치판의 환경·프로필·캐시 조건을 맞춘 A/B 측정.
2. P1-B: 빌드 후 파일 선택창의 조기 표시·취소·키보드·빠른 연속 이동·원격 provider 실사용 검증.
3. P1-C: JAR 작업의 기준선 및 데이터 보존 테스트, worker 격리·취소·안전한 결과 교체 설계.
4. P2-A 나머지: 실제 폴더에서 첫 목록 지연을 측정해 한도 8을 검증하거나 조정한다. 보이는 항목 우선 채우기, 빠른 이동 시 오래된 조회 취소는 미구현.
5. P2-B: 실제 검색에서 경로 열거·스냅샷·worker 시작·첫 배치 시간 분리 측정.
6. P2-D 나머지: SQL 파일이 많은 조건에서 목록 갱신과 활성화 시간을 측정해 한도 8을 검증한다. `migrateLegacy()`의 완료 버전·재시도 조건, 무효화 조건이 명확한 목록 캐시는 미구현이며, 이전을 한 번만 수행하도록 막거나 원본을 지우지 않는다는 제약을 유지한다.
7. P2-C: 시작창 전환 수명은 미구현.
