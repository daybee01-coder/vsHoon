# 성능 개선 6차: JAR 작업의 데이터 보존 기준선과 안전한 저장 교체

작성일: 2026-09-09. 대상: [성능 개선 가이드](performance-improvement-guide.md)의 P1-C.

## 이어받은 상태와 범위

- 작업 시작 시 HEAD는 `2ec7fa0`(1~5차 변경 커밋 완료)이며 작업 트리는 깨끗했다.
- 검증에는 기존 `.build/tools/node-v24.18.0`을 명령별 PATH로 사용했다. 시스템 Node·사용자 프로필·캐시는 변경하지 않았다.
- 가이드의 구현 순서 3번은 "JAR 격리처럼 구조 변경이 필요한 항목은 취소·데이터 보존 테스트를 먼저 마련한다"고 정한다. 이번 차수는 그 **선행 조건**만 다뤘다. **worker 격리는 구현하지 않았고, 따라서 이번 변경으로 확장 호스트 점유가 줄어들지 않는다.**
- `openZip`의 `readFileSync`, `extractAllEntries`의 동기 쓰기, `rebuildJarFromFolder`의 동기 읽기·`toBuffer()`는 그대로다. 진행률·취소도 아직 없다.
- P0 배포판 A/B 측정, P1-B 대화상자 실사용 검증, P2-A/P2-B의 남은 측정, P2-C, P2-D의 이전 로직은 이번 범위 밖이다.

## 변경

### 1. 기준선 테스트를 돌릴 수 있게 만들었다

`npm run test:decom`은 컴파일만 하고 있었고 이 확장에는 테스트가 하나도 없었다. 가이드도 "`npm run test:decom`은 현재 컴파일 명령뿐이므로 JAR 런타임 검증을 대체하지 않는다"고 적어 두었다. 스크립트를 다른 확장과 같은 `컴파일 + node --test` 형태로 바꿨다.

테스트를 만들려면 `zipUtil.ts`가 `vscode`를 간접 참조하는 것부터 끊어야 했다. `MANIFEST_DIRNAME`을 `manifest.ts`(→ `vscode` import)에서 가져오고 있었기 때문이다. 경로·항목 이름 규칙을 [entryPaths.ts](../extensions/vshoon-decom/src/entryPaths.ts)로 옮겨 `zipUtil.ts`가 `vscode` 없이 로드되게 했다. `manifest.ts`는 `MANIFEST_DIRNAME`을 그대로 재수출하므로 기존 import 경로는 바뀌지 않았다.

### 2. 저장 결과를 임시 파일로 교체한다

`rebuildJarFromFolder`는 `fs.writeFileSync(jarPath, zip.toBuffer())`로 원본 jar에 직접 썼다. 쓰기가 중간에 끊기면 원본이 반쯤 덮인 상태로 남는다. 같은 폴더의 `<jar>.decom-tmp`에 먼저 쓰고 원본 자리로 옮기도록 바꿨고, 실패 시 임시 파일을 지우고 원래 오류를 그대로 던진다.

- 최초 1회 `.decom-bak` 백업은 그대로 유지된다. 이 변경은 그 백업을 대신하는 것이 아니라, 백업 이후의 매 저장에서 원본이 깨지지 않게 하는 것이다.
- `rename`은 같은 폴더 안이라 파일 시스템 경계를 넘지 않는다. 프로세스가 죽어도 최악의 경우 `.decom-tmp`가 남고 원본은 온전하다.
- 메모리 사용량은 줄지 않는다. `toBuffer()`가 전체를 메모리에 담는 성질은 그대로이며, 이는 P1-C의 남은 작업이다.

### 3. 항목 경로 경계를 막았다

`extractAllEntries`는 zip 항목 이름을 `path.join(destDir, ...)`으로 그대로 이어 붙였다. 항목 이름은 아카이브를 만든 쪽이 정하는 값이라 절대 경로나 `..`이 들어 있을 수 있고, 그러면 캐시 폴더 밖의 사용자 파일을 덮어쓴다. 가이드의 P1-C 검증 목록에 있는 "엔트리 경로 경계" 항목이다.

- `safeEntryTarget`이 폴더 밖을 가리키는 항목을 거부한다. `..`은 결과가 폴더 안이 되더라도 거부한다 — 정상 jar에 없는 형태라 좁게 막는 편이 안전하다.
- 그런 항목이 있어도 jar 열기 전체를 실패시키지 않고 해당 항목만 건너뛴 뒤 이름을 호출부에 돌려준다. `jarProject.ts`가 그 목록을 Decom 출력 채널에 남긴다. 조용히 사라지지는 않는다.
- 반환형이 `string[]`에서 `{ extracted, skipped }`로 바뀌었고 호출부는 `jarProject.ts` 한 곳이다.
- **이 확장의 다른 경로를 감사한 것은 아니다.** 이번에 확인한 것은 `extractAllEntries`의 쓰기 대상 계산뿐이다.

## 검증 결과

- `npm run test:decom`: 컴파일 오류 0, 테스트 파일 2개·테스트 10개 통과. (이 확장의 첫 테스트다.)
- `npm run core -- exec -- eslint <신규·수정 파일 4개>`: 오류·경고 0.
- `git diff --check` 통과.
- 진행 중 발견해 고친 것: `noUncheckedIndexedAccess`와 무관한 컴파일 오류는 없었으나, 처음 작성한 픽스처가 실제로는 위험하지 않았다 — `adm-zip`은 항목을 **추가**할 때 `../`를 스스로 정리해서 그 형태의 악성 jar를 만들 수 없다. 드라이브 문자로 시작하는 이름은 그대로 남는 것을 확인해 그 형태로 바꿨다. `..` 형태의 거부는 `entryPaths` 단위 테스트가 담당한다.
- 왕복 후 항목이 원본과 **완전히 같지는 않다**는 것도 테스트로 고정했다. 재빌드는 캐시 폴더의 모든 폴더에 디렉터리 항목을 쓰므로 원본에 없던 중간 디렉터리 항목(`BOOT-INF/`, `META-INF/`, `static/`)이 생긴다. 기존 의도된 동작이며, 잃어버리는 항목이 없다는 쪽을 검증한다.
- 이 확장의 **기존** 파일들(`jarProject.ts`, `manifest.ts` 등)에 남아 있는 저작권 헤더 누락과 중괄호 경고는 이번 범위 밖이라 그대로 뒀다. 전면 재작성한 `zipUtil.ts`와 신규 파일에는 헤더를 넣고 중괄호를 보완했다.

테스트가 검증하는 내용:

1. [zipUtil.test.ts](../extensions/vshoon-decom/src/zipUtil.test.ts) — 중첩 라이브러리 jar와 디렉터리 항목을 가진 Spring Boot 모양 jar를 추출하면 디렉터리 항목을 뺀 모든 파일이 원본 바이트 그대로 나온다.
2. 왕복(추출 → 재빌드) 후 원본 항목이 하나도 사라지지 않고, `.class`·중첩 jar의 바이트가 같으며, 중첩 jar만 STORED(무압축)이고 일반 리소스는 아니다.
3. 캐시 폴더에서 수정·추가·삭제한 내용이 반영되고 `.decom`·`.vscode`는 jar에 들어가지 않는다.
4. 재빌드가 실패하면 원본 jar가 바이트 단위로 그대로 남고 `.decom-tmp`도 남지 않는다.
5. 절대 경로 항목은 쓰이지 않고 건너뛴 이름으로만 보고되며 캐시 폴더에는 정상 항목만 남는다.
6. [entryPaths.test.ts](../extensions/vshoon-decom/src/entryPaths.test.ts) — 구분자 정규화, 중첩 아카이브 판정, 메타 폴더 판정(`.decomposed`처럼 접두어만 같은 이름은 제외하지 않음), 그리고 `../`·절대 경로·드라이브 문자·빈 이름의 거부.

임시 폴더에서 만든 jar만 사용했고 실제 사용자 JAR·워크스페이스에는 접근하지 않았다. 실제 대형 JAR의 열기/저장 시간·최대 메모리 측정, `.class` 디컴파일(CFR) 경로, 저장 명령의 UI 흐름, 긴 Windows 경로에서의 실제 추출, 손상된 JAR·취소 시나리오는 이번 단계에서 수행하지 않았다. 제품 코어를 수정하지 않아 코어 빌드/layers/patch 저장도 실행하지 않았다. 패키징·커밋·원격 push는 하지 않았다.

## 남은 작업

1. P0: 동일 빌드 ZIP/설치판의 환경·프로필·캐시 조건을 맞춘 A/B 측정.
2. P1-B: 빌드 후 파일 선택창의 조기 표시·취소·키보드·빠른 연속 이동·원격 provider 실사용 검증.
3. P1-C 나머지: 큰 JAR의 열기/저장 기준선 측정 후 압축·해제를 worker/별도 프로세스로 격리하고, 파일 I/O 동시성과 `toBuffer()`의 메모리 사용을 제한한다. 진행률·취소·오류 복구를 함께 설계하고, 취소 시 임시 파일을 남기지 않는 경로를 이번 임시 파일 교체 위에 얹는다. 손상된 JAR·긴 Windows 경로·중첩 JAR 보존은 지금 테스트를 확장해 덮는다.
4. P2-A 나머지: 실제 폴더에서 첫 목록 지연을 측정해 한도 8을 검증하거나 조정한다. 보이는 항목 우선 채우기, 빠른 이동 시 오래된 조회 취소는 미구현.
5. P2-B: 실제 검색에서 경로 열거·스냅샷·worker 시작·첫 배치 시간 분리 측정.
6. P2-D 나머지: 파일이 많은 조건에서 목록 갱신·활성화 측정, `migrateLegacy()`의 완료 버전·재시도 조건, 무효화 조건이 명확한 목록 캐시.
7. P2-C: 시작창 전환 수명은 미구현.
