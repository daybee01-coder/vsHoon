# 추가 개발 12 — DeCom 고도화2

JAR 안의 `.class`를 일반 읽기 전용 Java 문서로 열고, JAR를 펼칠 때 백그라운드에서 미리 디컴파일해
영속 캐시에 저장하도록 확장했다. 준비된 소스는 VSearch 검색과 같은 JAR 안의 제한된 선언 이동에서
공유한다.

## 최종 동작

- `.class`는 `vshoon-decom:` URI의 Java 문서로 열린다. 일반 편집기의 줄 번호, 문서 검색, 복사,
  개요와 위치 이동을 그대로 사용한다.
- JAR 인덱스가 열리면 내부 클래스가 낮은 우선순위의 예약 목록에 들어가 한 건씩 처리된다. 사용자가
  직접 연 클래스는 대기열 앞으로 올라가며 진행 중인 백그라운드 작업을 선점한다.
- 디컴파일 결과는 확장 전용 전역 저장소의 `class-sources-v2`에 `.java`와 메타데이터 쌍으로 저장된다.
  같은 입력은 VShoon을 다시 실행해도 CFR를 다시 실행하지 않고 재사용한다.
- VSearch의 JAR 내부 검색은 입력 즉시 검색을 우선하기 위해 현재 비활성화했다. VSearch는 DeCom 캐시를
  조회하지 않으며, DeCom의 `listCachedSources` API는 다시 연결할 때를 위해 남겨 두었다.
- 문서 심볼은 디컴파일된 타입, 생성자와 메서드를 표시한다. `정의로 이동`은 준비된 같은 최상위 JAR
  안에서 호출의 수신 클래스, 인자 수와 추론 가능한 인자 타입이 맞는 선언을 찾는다. 타입을 확정할 수
  없는 오버로드는 점수가 같은 후보를 모두 반환한다.

## 소스 문서와 수명주기

`classSourceUri.ts`가 원본 `file:` 또는 `vshoon-jar:` 클래스 URI를 손실 없이 인코딩한다.
`ClassSourceService`는 `TextDocumentContentProvider`와 디컴파일 큐를 함께 소유한다. 기존
`decom.classViewer` custom editor는 호환 진입점으로 남아 있으며, 같은 읽기 전용 Java 문서로 넘긴 뒤
임시 패널을 닫는다.

가상 클래스는 선택한 outer/inner class 묶음만 임시 디렉터리에 기록한다. CFR 종료, 실패, 취소 뒤에는
즉시 삭제한다. CFR 프로세스도 VS Code 취소 토큰과 연결했다. JAR 새로고침, 관련 설정 변경, 확장 종료
시 활성 작업을 취소하고 오래된 작업이 뒤늦게 캐시를 게시하지 못하게 세대 번호를 검사한다.

## 영속 캐시

캐시 키에는 다음 입력을 반영한다.

- 대상 outer/inner class 묶음의 이름과 바이트
- CFR JAR의 SHA-256
- Java 실행 경로와 CFR 추가 옵션
- 추가 classpath 파일의 내용 또는 디렉터리 메타데이터

메타데이터에는 원본 클래스·소스 URI, 표시 경로, 최상위 JAR의 크기·수정 시각·SHA-256, 소스
SHA-256과 형식 버전을 기록한다. 소스와 메타데이터는 고유한 임시 파일을 거쳐 게시하고, 손상됐거나
부분적으로 남은 항목은 무시한다. 여러 창에서 캐시를 정리하거나 갱신하는 경우의 파일 경합도 허용한다.

캐시를 검색하거나 문서를 다시 열 때 최상위 JAR의 SHA-256을 검증한다. 용량은 기본 512MB이며 오래된
항목부터 삭제한다. JAR 하나에서 사전 처리할 클래스 수는 기본 5,000개다.

## VSearch 연동

DeCom은 활성화 결과로 버전 1의 제한된 `listCachedSources` API를 제공한다. VSearch는 현재 검색 범위,
파일 수, 파일별 크기와 총 64MB 제한을 전달하고 준비된 소스만 받는다. 검색 worker에는 캐시 파일의 OS
경로 대신 읽기 전용 URI와 소스 문자열을 전달하므로 확장 저장소 구조가 검색 결과에 노출되지 않는다.

JAR 결과는 확장 호스트와 Webview 양쪽에서 읽기 전용으로 취급한다. 미리보기 저장, 한 건 바꾸기와
모두 바꾸기는 거부한다. 사전 디컴파일이 진행 중이면 남은 작업 수를 상태줄에 표시하며, 완료 뒤 같은
검색을 실행하면 새 캐시가 결과에 포함된다.

## 설정과 명령

| 항목 | 기본값 | 역할 |
| --- | --- | --- |
| `vshoon.decom.precompileOnExpand` | `true` | JAR를 펼칠 때 사전 디컴파일 |
| `vshoon.decom.precompileMaxClasses` | `5000` | JAR 하나의 예약 상한 |
| `vshoon.decom.cacheMaxSizeMb` | `512` | 영속 소스 캐시 상한 |
| `Decom: 백그라운드 디컴파일 취소` | 명령 | 활성 백그라운드 작업과 대기열 취소 |
| `Decom: 디컴파일 소스 캐시 삭제` | 명령 | 캐시 삭제와 열린 소스 문서 갱신 |

새 설정과 명령은 `vshoon.decom.*` 접두사를 사용하며 영문·한글 package NLS 문자열을 제공한다.

- `extensions/vshoon-vsearch/src/decomSearch.ts`: 버전 확인과 범위가 제한된 DeCom API 호출

## 후속 개선 — 클래스 열기 지연

첫 적용 뒤 "class 파일 여는 데 로딩이 필요해 보인다"는 확인이 있어, 클래스 열기 경로를 다시 측정하고
줄였다.

### 고친 것

- **준비된 클래스는 큐를 거치지 않는다.** 소스 URI로 캐시 항목을 바로 찾는 인덱스를 추가했다. 이전에는
  캐시가 있어도 임시 디렉터리에 class 묶음을 다시 쓰고 지문을 다시 계산한 뒤에야 캐시를 확인했고, 그
  작업이 단일 작업 큐 안에서 실행돼 진행 중인 백그라운드 CFR가 끝날 때까지 기다렸다.
- **사용자가 연 클래스가 백그라운드 작업을 선점한다.** 실행 중인 사전 디컴파일을 취소하고 그 작업을
  대기열에 되돌린 뒤 사용자 요청을 먼저 처리한다. 되돌린 작업은 버려지지 않는다.
- **JAR를 펼칠 때 큐가 폭주하지 않는다.** 이전에는 최대 5,000개 작업을 한 번에 큐에 넣고 넣을 때마다
  정렬해 확장 호스트가 멈출 수 있었다. 이제 예약 목록에서 한 건씩 꺼내 처리하고, 우선순위는 사용자
  대기열과 백그라운드 대기열을 나눠 정렬 없이 구분한다.
- **최근에 연 소스는 메모리에 남긴다.** 상한은 48개이며 캐시를 지우면 함께 비운다.
- **내부 클래스는 바깥 클래스와 같은 문서·같은 캐시 항목을 쓴다.** CFR는 outer/inner 묶음을 하나의
  텍스트로 만들므로 `Foo$Bar.class`는 `Foo.java`를 연다. 디컴파일러 실행 횟수가 묶음당 한 번으로
  줄고, 이전에 `Foo$Bar.class`가 `Foo`의 소스를 자기 이름으로 표시하던 문제도 없어진다.
- **캐시가 오래 걸릴 때만 상태를 알린다.** 300ms 안에 끝나면 아무것도 표시하지 않고, 넘어가면 상태줄에
  디컴파일 중임을 표시한다.

### 측정

`javac`로 만든 최상위 클래스 40개(class entry 80개) JAR에 실제 CFR를 사용했다. 측정 머신은
Windows 11, JDK 25다.

| 경로 | 시간 |
| --- | --- |
| 같은 세션에서 다시 열기 | 0.1 ms |
| 재시작 후 열기(영속 캐시) | 2 – 4 ms |
| 사전 디컴파일이 도는 중에 준비된 클래스 열기 | 2 – 3 ms |
| 사전 디컴파일이 도는 중에 준비되지 않은 클래스 열기 | CFR 1회 실행 |
| 이전 구현이 캐시 적중에도 매번 하던 일(임시 파일 + 지문) | 3 – 5 ms |

준비된 클래스 열기에서 없앤 것은 임시 파일 왕복과 지문 계산(3–5ms), 그리고 진행 중인 CFR 작업이 끝날
때까지의 대기(측정 머신 기준 최대 약 5초)다.

### 남은 병목 — CFR 프로세스 실행 비용

준비되지 않은 클래스는 여전히 CFR를 한 번 실행해야 한다. 측정 머신에서 이 한 번이 약 5초였고, 원인을
분리한 결과 CFR의 작업이 아니라 **프로세스 생성 자체**였다.

| 실행 방식 | 시간 |
| --- | --- |
| `java -jar cfr.jar <class>` (Python subprocess, 콘솔 창 숨김 없음) | 0.3 초 |
| Node `spawn`, `windowsHide: false` | 0.3 초 |
| Node `spawn`, `windowsHide: true` (현재 구현) | 3.7 – 4.5 초 |
| `javaw.exe`, `windowsHide: true` | 0.35 초 |

`windowsHide: true`는 `CREATE_NO_WINDOW`로 프로세스를 만든다. 콘솔 창이 뜨지 않게 하려면 필요하지만,
이 머신의 보안 소프트웨어가 그렇게 만들어진 프로세스를 검사하면서 호출당 약 4초를 더한다. CFR 자체의
작업은 0.15초 수준이다.

`javaw.exe`로 바꾸면 창 없이도 빠르지만, JVM 시작이 실패할 때 콘솔 대신 모달 대화상자를 띄운다.
없는 JAR로 확인한 결과 출력 없이 64초 이상 멈췄다. 그래서 이번 단계에서는 바꾸지 않았다.

선택지는 세 가지이며, **1번(예외 등록)을 먼저 확인하기로 했다.** 코드 변경이 없고 원인이 맞는지 바로
검증되기 때문이다. 효과가 없거나 다른 환경에서도 재현되면 2번을 진행한다.

1. 측정 머신의 보안 소프트웨어에 JDK 실행 파일 예외를 등록한다. 코드 변경이 없고 이 머신에서만 유효하다.
   재측정은 `npm run test:decom`의 `real CFR decompiles a class read lazily from the virtual JAR`
   항목으로 한다. 예외 등록 전 기준값은 9.5 – 12초다.
2. 클래스마다 CFR를 실행하지 않고 묶음 단위로 한 번 실행한다(`--outputdir`). 모든 환경에서 사전
   디컴파일이 실행 횟수만큼 빨라지지만 변경 범위가 크고 부분 실패·디스크 사용량 처리가 필요하다.
3. Windows에서 `javaw.exe`를 쓰고 작업별 시간 제한을 함께 넣는다. 이 머신에서 가장 크게 개선되지만
   드문 오설정에서 대화상자가 뜰 수 있다.

### 함께 확인한 남은 문제

- `선언으로 이동`은 호출될 때마다 같은 JAR의 캐시 항목을 모두 읽고 해시로 검증한다. 클래스가 많은
  JAR에서는 한 번의 이동이 수천 건의 파일 읽기가 된다. 심볼 인덱스가 필요하며 이번 범위에 넣지 않았다.
- CFR 실행에 작업별 시간 제한이 아직 없다. 프로세스가 멈추면 큐가 그대로 막힌다.

## 후속 개선 — 패키지 새 창 성능

실제 패키지에서 새 창을 열었을 때 JAR 탐색과 클래스 열기뿐 아니라 창 전체가 느리다는 피드백을
재현 경로로 반영했다. 이전 구현은 Explorer가 펼친 JAR를 복원할 때 클래스 묶음마다 별도
`java -jar cfr.jar` 프로세스를 직렬 실행했다. 캐시가 있더라도 완료 여부를 클래스별 파일 조회로
다시 확인했고, 첫 캐시 사용은 원본 JAR 전체 SHA-256을 다시 계산했다. 패키지에서 프로세스 생성이
느린 환경에서는 백그라운드 사전 처리가 오히려 새 창의 지속적인 부하가 됐다.

변경한 동작은 다음과 같다.

- JAR 하나의 사전 디컴파일을 CFR/JVM 한 번의 `--outputdir` 실행으로 묶었다. 생성된 Java 파일을
  가상 class URI에 다시 연결해 기존 영속 캐시와 VSearch가 그대로 사용한다.
- Explorer 복원 직후에는 5초 동안 CFR를 시작하지 않는다. 사용자가 클래스를 열거나 에디터를
  전환하거나 커서·선택을 움직이거나 창으로 돌아오면 실행 중인 일괄 작업을 취소한다. 직접 연 클래스는
  먼저 처리하며, 일괄 작업은 다시 5초의 유휴 시간 뒤 시작한다.
- 일괄 작업이 끝나면 원본 JAR의 경로·크기·수정 시각, CFR와 설정 identity를 완료 마커에 저장한다.
  새 provider와 새 service가 만들어지는 재시작 조건에서도 마커가 맞으면 CFR와 클래스별 캐시 검사를
  모두 건너뛴다.
- 캐시 적중 판정에서 원본 JAR 전체 SHA-256을 제거하고 크기와 수정 시각을 사용한다. VSearch와 선언
  이동이 같은 JAR의 캐시를 여러 건 검사할 때도 한 요청 안에서는 원본 stat을 한 번만 수행한다.
- 설정한 클래스 묶음 상한을 넘은 JAR는 전체 CFR 실행을 시작하지 않는다. 이런 JAR는 사용자가 직접
  연 클래스만 처리하므로 새 창의 백그라운드 부하를 제한한다.
- Windows에서 기본 `java` 또는 `java.exe`를 사용하면 같은 JDK의 `javaw.exe`를 우선 실행한다.
  `javaw.exe`가 없거나 실행이 거부되면 기존 `java`로 자동 복귀하고, 사용자가 다른 이름의 실행 파일이나
  스크립트를 명시한 경우에는 바꾸지 않는다.

실제 CFR 검증은 `BOOT-INF/classes` 구조의 JAR를 `--outputdir`로 일괄 디컴파일해 패키지 경로의
Java 소스를 생성하는 경우까지 포함한다. 63개 Java 소스를 가진 `gson-2.8.0.jar`의 별도 구조 측정에서는
클래스마다 프로세스를 만들지 않고 한 번의 JVM 실행으로 63개 소스를 생성했으며 2.45초가 걸렸다.
이 수치는 셸 실행 기준이므로 패키지 체감 시간과 동일한 값으로 간주하지 않는다. 같은 Node
`spawn(..., { windowsHide: true })` 조건의 비교에서는 63개 소스 일괄 생성이 `java.exe` 7.1초,
`javaw.exe` 3.1초였고 두 실행 모두 종료 코드 0과 동일한 63개 결과를 만들었다.

| 항목 | 명령 | 결과 |
| --- | --- | --- |
| DeCom 컴파일·단위 테스트 | `npm run test:decom` | 36개 통과, 실제 CFR 일괄·단일 디컴파일과 provider 재시작 마커 재사용 포함 |
| VSearch 컴파일·단위 테스트 | `npm run test:vsearch` | 8개 통과, matcher 18개 검사 포함 |
| 변경 TypeScript ESLint | `npm run core -- exec -- eslint ...` | 통과 |
| 데스크톱 smoke | `npm run smoke:decom` | 통과 — 읽기 전용 VFS, 캐시, 중첩 JAR와 원본 불변 확인 |
| 오버레이·패치 동기화 | `npm run sync:check -- --offline` | 538개 파일 동기화, 통과 |

프로젝트 지침에 따라 패키징은 실행하지 않았다. 다음 패키지에서 새 창 복원, JAR 펼치기, 첫 클래스와
캐시된 클래스 열기를 실제로 다시 확인해야 한다.

## 후속 개선 — 선언 이동 인덱스와 작업 시간 제한

앞 단계에서 남겨둔 두 문제를 처리했다. `선언으로 이동`이 호출 한 번마다 같은 JAR의 캐시 항목을 모두
읽고 해시로 검증하던 문제와, CFR 실행에 작업별 시간 제한이 없어 프로세스가 멈추면 큐가 그대로
막히던 문제다.

### 선언 이동 — JAR별 타입 인덱스

- Java 텍스트 분석을 `javaSymbols.ts`로 분리했다. `classNavigation.ts`에는 문서 심볼과 선언 이동
  provider만 남으므로 소스 서비스가 같은 파서를 순환 참조 없이 사용한다.
- 캐시에 JAR별 타입 인덱스 파일을 추가했다. 준비된 소스가 선언하는 타입 이름을 `{소스 URI, 캐시 키}`
  목록에 대응시킨다. 일괄 사전 디컴파일은 JAR 하나의 인덱스를 한 번에 기록하고, 사용자가 직접 연
  클래스는 캐시에 게시할 때 자기 항목만 갱신한다. 인덱스가 없는 기존 캐시는 그 JAR에서 처음 이동할 때
  한 번 만들어 저장한다.
- 이동은 먼저 호출 지점에서 선언을 가질 수 있는 타입 이름만 계산한다. 수신 변수의 타입, `this`,
  `super`, 생성자, 타입 참조를 구분하며, 대상을 알 수 없으면 캐시를 전혀 읽지 않는다.
- 후보 판정 규칙은 그대로다. 수신 클래스, 인자 수, 리터럴·변수에서 추론한 인자 타입을 비교하고
  점수가 같은 오버로드는 모두 돌려준다. 달라진 것은 비교 대상 소스를 고르는 방법뿐이다.
- 캐시를 지우면 인덱스도 함께 사라진다. 용량 정리로 사라진 항목을 가리키는 줄은 읽을 때 건너뛴다.

같은 캐시 데이터에서 두 접근 방식을 비교했다. 메서드 30개짜리 클래스를 준비된 소스로 만들고, 그중
한 선언을 찾는 데 드는 시간이다. 측정 머신은 Windows 11이다.

| 준비된 클래스 수 | 캐시 전체 조회(이전) | 타입 인덱스 조회(현재) | 인덱스 파일 크기 |
| --- | --- | --- | --- |
| 1,000개 | 856 ms, 1,000건 읽기 | 2.5 ms, 1건 읽기 | 73 KB |
| 3,000개 | 3,146 ms, 3,000건 읽기 | 6.2 ms, 1건 읽기 | 225 KB |

### 디컴파일 작업 시간 제한

- 클래스 하나를 처리하는 작업에는 절대 시간 제한을 적용한다. 제한을 넘기면 CFR 프로세스를 취소하고
  그 요청만 실패시킨 뒤 큐는 다음 작업으로 넘어간다. 취소를 무시하는 작업이 있어도 큐는 풀린다.
- JAR 일괄 실행에는 진행이 없을 때만 걸리는 제한을 적용한다. 출력 디렉터리에 만들어진 Java 파일 수가
  늘어나면 제한 시간을 다시 시작하므로, 오래 걸리는 큰 JAR는 중단하지 않고 아무것도 쓰지 않는 실행만
  중단한다. 시간 제한으로 중단한 일괄 작업은 사용자 선점으로 중단한 작업과 달리 대기열로 되돌리지
  않으므로 같은 창에서 계속 다시 시도하지 않는다.
- `vshoon.decom.decompileTimeoutSec`로 조정한다. 기본값은 120초이며 0이면 제한하지 않는다.

### 검증

| 항목 | 명령 | 결과 |
| --- | --- | --- |
| DeCom 컴파일·단위 테스트 | `npm run test:decom` | 39개 통과, 타입 인덱스 조회·재생성, 멈춘 클래스 작업의 큐 해제, 아무것도 쓰지 않는 일괄 실행 중단 추가 |

| 오버레이·패치 동기화 | `npm run sync:check -- --offline` | 539개 파일 동기화, 통과 |
| 데스크톱 smoke | `npm run smoke:decom` | 통과 — 읽기 전용 VFS, Java 편집기 줄 번호, 중첩 JAR, 원본 불변 |

smoke의 임시 CFR 입력 검사도 고쳤다. 일괄 사전 디컴파일이 먼저 끝나면 클래스는 준비된 캐시에서 바로
열리고 임시 입력 디렉터리를 만들지 않는데, 대기 함수만 그 디렉터리가 존재하기를 요구해 이 순서에서
실패했다. 스크립트 끝의 최종 검사와 같은 불변식인 "남은 임시 입력이 없을 것"으로 맞췄다. 실패했던
실행의 프로필에는 완료 마커와 준비된 소스 2건이 있고 임시 입력 디렉터리는 없었다.

실제 패키지에서의 체감 재확인은 아직 남아 있다. 이번 변경도 VShoon 소유 확장과 smoke 스크립트만
수정하므로 새 upstream 패치나 `patch:save`는 필요하지 않다.

## 제한

- 사전 디컴파일은 JAR마다 CFR 프로세스를 한 번 실행하며 동시 실행 수는 1이다. 큰 JAR는 완료까지
  시간이 걸릴 수 있고 클래스 묶음 상한을 넘은 JAR는 직접 연 클래스만 처리한다.
- 선언 이동은 타입 인덱스에 있는 같은 JAR의 준비된 소스만 본다. 주석·문자열을 제외한 Java 텍스트에서
  직접 호출을 분석하고 수신 변수 타입, 인자 수와 리터럴·변수 타입을 비교한다. 연쇄 호출의 반환 타입, 모든 generic 타입, JVM descriptor, 전체 상속
  관계, 동적 호출과 사용처를 분석하는 완전한 Java 의미 분석은 제공하지 않는다.
- VSearch는 검색을 시작한 시점에 준비된 캐시만 사용한다. 상태줄에 대기 작업이 남아 있으면 완료 뒤
  검색을 다시 실행해야 한다.
- 대응하는 `-sources.jar` 자동 탐색과 원본 소스 우선 표시는 제공하지 않는다.
- 시간 제한은 진행이 멈춘 실행을 끊을 뿐 실패 원인을 진단하지 않는다. 중단된 JAR의 일괄 처리는 창을
  다시 열거나 캐시를 지운 뒤에 다시 시도한다.
