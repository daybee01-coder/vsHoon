# 추가 개발 20 — Java 소스 선언 이동과 검색 사전 인덱싱

작성일: 2026-10-28.
후속 보완: 2026-11-04.

## Java 소스 선언 이동

기존 선언 이동 provider는 `vshoon-decom:` 디컴파일 문서에만 등록되어 있었다. 일반 `file:` Java
문서에도 동작하는 소스 인덱스와 definition provider를 DeCom 내장 확장에 추가하고 프로젝트 시작 시
활성화한다. Ctrl+클릭과 F12가 사용하는 upstream 선언 이동 경로를 그대로 사용한다.

- 같은 파일의 메서드, 수신 변수의 타입을 알 수 있는 다른 소스 파일의 메서드, 타입과 생성자를 찾는다.
- 같은 패키지, 명시적 import, wildcard import로 대상 소스를 고른다. 인자 수와 추론 가능한 인자 타입으로
  오버로드를 구분한다. 후보 소스의 본문은 보관하지 않고 타입·메서드 심볼만 인덱스에 남긴다.
- Java 파일을 처음 열면 워크스페이스를 4개씩 비동기로 읽어 준비한다. 직접 이동할 때는 대상 타입 이름의
  Java 파일을 먼저 찾으므로 전체 사전 처리가 끝나기를 기다릴 필요가 없다.
- 같은 파일의 선언은 파일 검색이나 사전 인덱싱을 기다리지 않고 즉시 반환한다. 다른 파일의 후보 읽기도
  4개로 제한하며 취소 요청과 워크스페이스 변경을 확인한다.
- 워크스페이스 폴더가 바뀌면 새 인덱싱 작업으로 대기 대상을 교체한다. 변경 전 파일 읽기의 결과나 오류가
  새 워크스페이스의 인덱스를 덮어쓰지 않도록 세대를 확인한다.
- 생성·수정·삭제 감시와 미저장 문서 변경으로 인덱스를 갱신한다. 입력 중 재분석은 250ms 뒤로 합치고,
  선언 이동을 요청하면 열린 대상 문서의 최신 버전을 즉시 반영한다.
- 공용 Java 파서는 한 줄에 여러 멤버가 있는 소스, annotation과 여러 줄 매개변수를 처리한다. 메서드
  본문의 호출을 선언으로 오인하지 않도록 타입 본문의 중괄호 깊이를 확인한다. 주석·문자열에서는 이동하지 않는다.
- Red Hat Java 확장(`redhat.java`)의 설치 여부만으로 내장 이동을 끄던 조건을 제거했다. 설치되어도
  초기화에 실패하거나 아직 시작하지 않은 환경에서 내장 이동이 계속 동작한다. upstream이 provider 결과를
  합치고 중복 위치를 제거하므로 기존 언어 서버도 함께 사용할 수 있다.
- Spring 방식의 매개변수 어노테이션과 메서드 뒤에 선언한 수신 필드를 처리한다. `return service.save()`의
  `return`을 수신 객체의 타입으로 오인하던 추론도 수정했다.

이 기능은 Java 언어 서버가 없는 환경을 위한 제한된 fallback이다. 외부 의존성, 상속 관계 전체,
generic 의미 분석, 연쇄 호출의 반환 타입, static import, 지역 변수의 완전한 범위 분석은 제공하지 않는다.
대규모 Java 프로젝트의 정확한 의미 분석에는 Java 언어 서버가 필요하다. 대상은 로컬 `file:` 소스이며,
최대 20,000개, 파일당 2MiB까지 읽는다. `.git`, `node_modules`, `target`, `build`, `out`, `dist`는 제외한다.
JAR 내부 선언 이동은 기존 provider가 계속 담당한다.

## 검색 사전 인덱싱과 최신 파일 확인

기존 검색은 검색창을 연 뒤에야 내용을 미리 읽었고 검색창을 닫으면 캐시도 사라졌다. 파일 내용의
재검사는 2초 주기였으며, 직전 검색에 일치한 파일만 재검색하는 경로는 감시 이벤트가 늦으면 변경을 놓칠 수 있었다.

- 내장 확장을 `*`로 활성화하고 프로젝트가 열리면 즉시 워크스페이스를 미리 읽는다. 검색창 생성이나
  5초 타이머를 기다리지 않는다. worker와 메모리 캐시는 확장 수명에 귀속된다.
- 각 로컬 프로젝트의 `.vshoon/cache/vsearch-v1`(11-05부터 `vsearch-v2`)에 텍스트·trigram 필터·파일 메타데이터를 저장한다.
  재시작하면 메타데이터가 일치하는 캐시를 복원해 원본 읽기와 인덱스 생성을 생략한다. 변경된 파일만
  원본에서 다시 읽는다. 캐시 버전·checksum·입력 형식을 검증하고 임시 파일 교체로 기록한다.
- 파일 생성·수정·저장 알림을 100ms 단위로 합쳐 바로 다시 인덱싱하며 삭제 알림은 캐시에서도 제거한다.
  미저장 문서는 검색 시 최신 문서 스냅샷을 사용하고, 디스크에는 저장된 파일의 데이터만 기록한다.
- 파일 내용과 함께 1KiB의 trigram 필터를 만든다. 3글자 이상의 ASCII 일반 검색은 해당 조합이 없는
  파일에서 전체 매칭을 생략한다. 해시 충돌은 추가 후보를 허용하므로 결과를 빠뜨리지 않는다.
- 정규식·비ASCII·짧은 검색어는 기존 매칭을 사용하고, 미저장 문서는 디스크 인덱스를 건너뛰어 최신 텍스트를 검색한다.
- 매 검색에서 파일 목록을 다시 열거하고, 캐시된 파일의 크기·mtime·ctime·inode를 확인한다. 신규 파일과
  메타데이터가 달라진 파일만 다시 읽고 인덱싱한다. 감시 이벤트와 관계없이 삭제 파일을 제외한다.
- 직전 결과에 한정하는 최적화와 오래된 파일 목록 재사용을 제거했다. 검색 범위·마스크·제외 설정도 매번 적용한다.
- 파일 내용과 필터는 기존 256MiB 근사 상한 안에서 LRU로 보관한다. 사전 읽기는 약 8ms 단위로 양보해
  사용자 검색을 우선하며, 검색 취소와 정규식 worker 시간 제한은 유지한다.

메모리는 기존 256MiB 근사 상한을 사용하고 프로젝트별 디스크 캐시도 256MiB를 넘으면 오래된 항목부터
정리한다. 캐시 폴더에는 `*`를 담은 `.gitignore`를 생성하고 검색·파일 감시에서 자체 캐시를 제외한다.
읽기 전용 프로젝트나 손상된 캐시에서는 원본 읽기로 계속 검색한다. 기존 파일 수·크기 제한과 제외 규칙은
유지한다. 파일 목록 열거와 stat 비용은 검색마다 발생하므로 느린 디스크나 매우 큰 범위에서는 여전히
시간이 걸릴 수 있다. 읽는 도중 다른 프로그램이 파일을 수정하는 경우까지 원자적 스냅샷을 보장하지 않는다.

## 검색 전용 데스크톱 창

> 2026-11-04 재점검에서 사용자 요청에 따라 모달 팝업으로 되돌렸다. 아래 [재점검](#2026-11-04-재점검) 참조.

다시 열기 명령은 기존 보조 창을 표시하며 검색 결과는 메인 편집기의 첫 번째 그룹으로 연다.
DBConn·VSsh는 기존 모달을 사용하고 일반 VS Code에서는 표준 편집기 탭으로 열린다.

렌더링을 제외한다. 준비 시간 표는 내용 읽기·인덱스 생성·저장 또는 복원을 측정하며 앱 시작과 목록 열거는
제외한다. 사용자 프로젝트의 측정은 아니며 전체 검색창의 속도가 이 비율로 개선된다는 의미는 아니다.

같은 파일·다른 파일의 메서드와 미저장 호출·대상 문서의 줄 이동을 확인한다. 처음부터 `.code-workspace`로

사전 읽기 후 외부 수정, 파일 생성·삭제, 미저장 내용 반영을 검사한다. 성공하면 프로필을 삭제한다.
후속 smoke는 실제 renderer에 Ctrl+마우스 클릭과 F12 입력을 보내고 이동 후 활성 문서와 커서 위치를
확인한다. 비활성 Java 서버 확장 fixture도 설치해 설치 여부가 fallback을 막지 않는지 검사한다.
검색창을 열기 전 파일을 생성·수정·삭제하고 프로젝트 캐시의 즉시 반영을 확인하며, 검색 전용 창의
네이티브 창 ID와 IDE 밖의 실제 위치, 메인 창에 모달 배경이 없는지 검사한다. 사용자 프로젝트의
정확한 실패 코드와 체감 속도는 별도 재현 확인 대상이다.

2026-10-28 DeCom 재검사 중 기존 테스트의 임시 디렉터리 삭제 hook에서 Windows `ENOTEMPTY`가 한 번
발생했다. 기능 assertion 실패는 없었으며, 테스트를 수정하지 않고 전체를 재실행해 45개 통과를 확인했다.
첫 VSearch 컴파일의 중괄호 오류와 ESLint의 기존 extension 진입점 헤더 누락도 수정 후 통과했다.

2026-11-04에는 같은 패키지와 무관한 패키지의 구분, 선언 위치 수정과 메서드 삭제 테스트를 보강해
최종 47개 통과를 확인했다. 데스크톱 테스트 보강 중에는 주석 속 단어를 선택하던 테스트 위치를 수정했고,
upstream 테스트 호스트가 단일 폴더에서 새 워크스페이스로 전환하지 못하는 제한에 맞춰 처음부터
워크스페이스 파일로 실행하도록 바꿨다. 대기 루프의 이벤트 리스너 누적도 제거했다. 최종 데스크톱 검증은
모두 통과했으며 이번 검증에서 만든 임시 프로필은 정리했다.

지적사항 반영 후에는 실제 Ctrl+클릭/F12와 자동 캐시 갱신, IDE 밖 검색 창 이동까지 통과했다.
이 과정에서 검증용 Java 확장의 버전 선언, 보조 창의 `about:blank` 식별과 Electron에서 지원하는
창 이동 방식에 맞춰 테스트 드라이버를 수정했다. 기존 DBConn·VSsh 모달의 실제 열기와 layout 복원도
별도로 재확인했다. 실패한 시도를 포함해 이번 작업에서 만든 임시 프로필은 모두 정리했다.

기존 16·19번 작업의 수정 파일과 패치 등을 보존했다. 후속 검색 창 변경으로 VSH-0010이 소유한
`mainThreadWebviewPanels.ts`, `webviewWorkbenchService.ts`를 최소 수정하고 `npm run patch:save`로
기록했다. patch 장부와 capability 문서도 함께 갱신한다. 패키징, 커밋, 원격 push는 실행하지 않았다.

## 2026-11-04 재점검

### Java 선언 이동이 거의 동작하지 않던 원인

Ctrl+호버의 밑줄 링크와 F12·우클릭 이동은 같은 definition provider 결과를 쓴다. 결과가 비면 링크도
표시되지 않는다. 실제 호출 위치 22,871곳에 resolver를 돌려 보니 31%(7,162곳)만 해석했다.

- 연쇄 호출(`a.get().save()`)의 수신 객체를 현재 클래스로 오인했다.
- 상위 클래스·인터페이스에 선언된 메서드(`form.getLang()`, `super.getLogger()`)를 찾지 못했다.
- 필드, enum 상수, 지역 변수, 매개변수로는 이동하지 않았다. 생성자를 선언하지 않은 클래스의 `new X()`도 실패했다.
- 외부 JAR 타입(`RequestAttestationKey`, `MDC` 등)은 대상 자체가 없었다.
- 요청마다 같은 문서의 주석 마스킹과 타입 범위 분석을 여러 번 반복해 큰 파일에서 느렸다.

수정 내용:

- 공용 resolver(`javaSymbols.ts`)가 `extends`/`implements`를 기록하고 상위 타입을 가까운 순서로 탐색한다.
  암시적 호출은 바깥 클래스까지 확인한다.
- 필드(한 문장의 여러 선언자 포함), enum 상수, 같은 멤버 안의 지역 변수·매개변수 선언으로 이동한다.
  `field.member`는 필드 선언 타입을 따라가고, 상속 필드의 타입도 수신 객체 타입으로 쓴다.
- 반환 타입을 알 수 없는 연쇄 호출은 인덱스가 모두 준비된 뒤에만 같은 이름·인자 수의 메서드 후보를
  최대 20개 보여 준다. 부분 인덱스에서는 추측하지 않는다.
- 생성자가 없으면 클래스 선언으로 이동한다. 참조 인자 타입이 다르면 하위 타입일 수 있으므로 후보에서
  제외하지 않고 점수만 낮춘다.
- 소스에서 찾지 못하면 import(명시, wildcard, 같은 패키지)로 FQCN을 만든다. 워크스페이스 JAR의 central
  directory 색인에서 클래스를 찾아 기존 Decom JAR VFS와 디컴파일 문서의 해당 메서드·필드로 이동한다.
  JAR 색인은 소스 사전 인덱싱이 끝난 뒤 백그라운드에서 4개씩 읽는다. JAR 변경이나 폴더 변경 시 다시 만든다.
- 마스킹·타입 범위·중괄호 깊이·심볼 분석 결과를 문서 내용 기준으로 재사용한다.

같은 22,871곳 기준 소스 해석은 11,024곳(48%), JAR 대상까지 포함하면 15,700곳(68.6%)이다. 전체 실행
시간은 116.4초에서 3.4초로, 요청당 p99는 23ms에서 1ms로 줄었다. 남은 대상은 주로 JDK 타입(`String`,
`Map` 등)과 반환 타입을 알 수 없는 연쇄 호출이다. JDK 소스와 classpath 해석은 여전히 Java 언어 서버가
필요하다. JAR 대상으로 처음 이동하면 해당 JAR가 열리며, 기존 `vshoon.decom.precompileOnExpand` 설정에 따라
백그라운드 디컴파일이 예약된다.

### JSP·JavaScript 파일 간 함수 이동

FIDO의 JSP 페이지는 `resources/js/common.js` 등의 전역 함수(`goPage`, `alertPopup` 등)를 호출한다.
upstream JavaScript 서비스는 `jsconfig.json`이 없으면 열린 파일끼리만 연결하므로 다른 파일의 전역 함수로
이동하지 못했다. `.jsp`는 upstream에서 `html` 언어로 열리며 페이지 안의 script만 해석된다.

DeCom 확장에 JavaScript·HTML·JSP 문서용 definition provider를 추가했다(`scriptSymbols.ts`,
`workspaceScriptNavigation.ts`). 워크스페이스 `*.js/*.mjs/*.cjs/*.jsx`에서 `function name()`,
`name = function`, `obj.name = function`, 화살표 함수 대입, `name: function`, 객체·클래스 메서드, `class`
선언을 이름으로 색인한다. 주석·문자열 안에서는 이동하지 않는다. 같은 파일·페이지의 선언을 먼저 쓰고,
없으면 다른 스크립트의 같은 이름 선언으로 이동한다. 같은 이름이 30개를 넘으면 결과를 내지 않는다.
`*.min.js`와 `node_modules`, `bower_components`, `target`, `build`, `out`, `dist`는 제외한다. 처음 요청할 때
색인을 만들고 이후 파일 감시와 저장으로 갱신한다. 이름 기반 fallback이므로 같은 이름의 함수가 여러
파일에 있으면 후보 목록(peek)으로 보여 준다. upstream이 같은 위치의 결과를 합친다.

FIDO 스크립트 134개 색인은 244ms였다. JSP·HTML 160개와 스크립트의 전역 형태 호출 13,832곳 중 7,896곳은 같은
파일, 4,609곳(33%)은 다른 스크립트의 선언으로 연결된다. 남은 1,327곳은 주로 `Uint8Array`, `Error` 같은
내장 객체와 콜백 매개변수다.

### 검색이 입력마다 느리던 원인

검색어를 바꿀 때마다 `findFiles('**/*')`로 파일 목록을 다시 열거하고 worker가 모든 캐시 항목을 `stat`했다.
FIDO에서 `stat` 한 바퀴만 약 250ms였고 실제 매칭은 수십 ms였다. 또 후보 파일마다 줄 단위로 나눈 뒤에야
일치 여부를 확인했다.

- 워크스페이스 파일 목록을 메모리에 두고 생성·삭제 감시 이벤트로 즉시 고친다. 생성 이벤트가 몰리면
  1초 뒤 다시 열거해 제외 설정을 반영한다. 마스크와 디렉터리 범위는 메모리 목록에서 거른다.
  워크스페이스 밖 디렉터리, 경로가 들어간 마스크, 목록이 `maxFiles`에서 잘린 경우에는 기존 `findFiles`를 쓴다.
- 최근 5초 안에 확인한 캐시 항목은 다시 `stat`하지 않는다. 결과로 보낼 파일만 디스크와 다시 비교해
  오래된 줄을 보여 주지 않는다. 검색창을 열거나 IDE 창으로 돌아오면 목록 재열거와 전체 재검증을
  백그라운드에서 8ms 단위로 나눠 실행한다.
- 일반 검색어는 파일 전체에 일치가 없으면 줄로 나누지 않고 건너뛴다.

FIDO 파일 3,442개를 미리 읽은 상태에서 worker 매칭만 측정한 결과다. 파일 목록 열거 시간은 제외했다.

| 검색어 | 결과 파일 | 매번 전체 `stat` | 변경 후 |
| --- | ---: | ---: | ---: |
| `getAAID` | 20 | 87.4ms | 5.7ms |
| `logger` | 136 | 123.6ms | 16.6ms |
| 없는 문자열 | 0 | 114.9ms | 2.3ms |
| `get` | 826 | 156.5ms | 75.3ms |

변경 전에는 이 시간에 매 입력의 파일 목록 열거가 더해졌다. 결과가 많은 짧은 검색어는 결과 전달과
렌더링이 대부분을 차지한다. 외부 프로그램의 변경은 파일 감시 이벤트로 반영된다. 감시 이벤트가 누락되면
최대 5초 또는 창 복귀 재검증까지 반영이 늦을 수 있다. 저장하지 않은 편집 내용은 계속 즉시 반영한다.

### 검색창을 다시 팝업으로

VSearch 선언에서 `presentation: "window"`를 제거해 DBConn·VSsh와 같은 모달 팝업으로 연다. 사용자는 팝업을
선호하며, 화면 밖으로 옮길 수 없다면 잘려도 IDE 경계를 넘어 움직이기를 원했다.

VSH-0010의 `ModalEditorPart` 끌기·크기 조절·재배치 clamp가 VShoon 레이아웃에 경계를 먼저 묻는다.
선언된 번들 패널은 창 경계를 넘어 잘린 채 놓일 수 있다. 다시 잡을 수 있도록 머리글 160×48px는 창 안,
제목 표시줄 아래에 남는다. 일반 모달 편집기는 upstream clamp를 그대로 쓴다. `presentation: "window"`
capability는 유지하지만 현재 사용하는 번들 패널은 없다.

## 영속 stub 인덱스 (IntelliJ 방식)

IntelliJ는 파일마다 선언만 뽑은 stub 인덱스를 디스크에 두고, VFS의 수정 시각이 바뀐 파일만 다시
파싱한다. 같은 방식으로 Java 소스 선언, JAR 클래스 목록, 스크립트 함수 선언을 작업 영역 저장소
(`context.storageUri/index/*.json`)에 남긴다. 작업 영역이 없으면 메모리에만 둔다.

| 파일 | 내용 | 키 |
| --- | --- | --- |
| `java-stubs.json` | 소스별 선언(`SourceSymbol`)과 package·import | 소스 URI, `mtime:ctime:size` |
| `jar-classes.json` | JAR별 최상위 클래스 FQCN | JAR URI, `mtime:size` |
| `script-declarations.json` | 스크립트별 함수·메서드·클래스 선언 위치 | 스크립트 URI, `mtime:size` |

- `StubCache`(`extensions/vshoon-decom/src/stubCache.ts`)가 저장한다. 변경 후 2초 모아 임시 파일에 쓰고
  `rename`으로 바꾼다. 손상·다른 형식 버전(`java-stub-1` 등)은 버리고 다시 파싱한다.
- 시작 시 파일은 `stat`만 하고 스탬프가 같으면 읽지도 파싱하지도 않는다. 열린 문서는 계속 버퍼 내용이
  우선한다. 전체 탐색이 끝나면 없어진 파일 항목을 지운다.
- `javaSymbols`나 `scriptSymbols`의 결과 형태를 바꾸면 각 형식 상수를 올려야 한다.

FIDO(Java 소스 424개, JAR 431개)에서 같은 로직을 Node로 측정했다.

| 항목 | 첫 실행 | 다음 실행 |
| --- | --- | --- |
| JAR 클래스 목록 (84,656개) | 4,856ms | 46ms |
| Java 선언 | 262ms | 34ms |

이전에는 매 실행마다 JAR 431개의 중앙 디렉터리를 다시 읽어, 실행 직후 라이브러리 클래스로의 첫 이동이
수 초 기다렸다. `npm run test:decom` 55개(저장·재사용·스탬프 변경·형식 변경·손상 파일 1개 추가)와
`npm run smoke:java-search`가 통과했다. smoke 종료 후 임시 프로필 삭제는 이번에도 `EPERM`이라 직접 지웠다.

## 2026-11-05 검색 보완

20번 검색 변경을 다시 검토해 다음을 고쳤다.

- **감시 제외 폴더 판정**: 빌드 산출물 폴더(`build`, `out`, `target` 등) 판정이 파일의 전체 경로를 봐서,
  프로젝트가 `D:\build\...`처럼 그런 이름의 폴더 아래 있으면 모든 수정·생성 이벤트가 무시됐다. 이제 가장
  가까운 워크스페이스 루트 아래의 폴더만 본다(`indexablePath.ts`).
- **저장마다 캐시 폴더 정리**: 감시 이벤트로 다시 읽을 때마다 `prune`이 캐시 폴더 전체를 `readdir`·`stat`해
  worker가 검색을 처리하지 못했다. 사전 읽기가 끝났을 때, 또는 상한의 1/16 이상 기록했을 때만 정리한다.
- **검색 시간 제한**: 15초 제한에 디스크 읽기 시간이 포함돼, 캐시가 빈 상태에서 큰 범위를 읽으면 정규식과
  관계없이 worker가 종료되고 같은 실패가 반복될 수 있었다. worker가 검색 중 1초마다 진행을 알리고, 응답이
  15초 끊겼을 때만 종료한다. 종료한 뒤에는 사전 읽기를 다시 시작한다.
- **바이너리 파일 읽기**: JAR 등을 끝까지 읽은 뒤 앞 8KiB로 바이너리를 판정했다. 아카이브·이미지·실행 파일
  확장자는 읽지 않고, 64KiB를 넘는 파일은 앞 8KiB만 먼저 읽어 바이너리이면 나머지를 읽지 않는다.
- **대량 삭제**: 삭제 이벤트마다 파일 목록 전체를 훑었다. 목록에 있던 파일이면 그 항목만 지우고, 폴더일 때만
  하위 경로를 찾는다. 이때 하위 파일의 메모리·프로젝트 캐시도 함께 버린다.
- **인덱싱 비용**: trigram 계산을 앞의 두 글자를 이어 받는 방식으로 바꿨다(같은 비트). 바이너리 판정은
  native `indexOf`, UTF-8 디코더는 공유 인스턴스를 쓴다.

프로젝트 캐시가 텍스트까지 보관할 가치가 있는지 측정했다. 2,000개 파일(파일당 200줄)에서 원본 읽기와 인덱스
생성은 약 1,000ms, 프로젝트 캐시 복원은 약 370ms였다. 차이의 대부분은 trigram 생성(305ms)이었고 위 변경으로
81ms가 됐다(인덱스만 별도 측정). 복원이 여전히 빠르므로 캐시 형식은 유지한다. 개발 PC의 OS 디스크 캐시를
비우지 않은 합성 측정이며 파일 읽기 시간은 실행마다 크게 달랐다.

- **결과 목록 가상 스크롤**: 일치 1건마다 DOM 행을 만들어 최대 20,000행까지 그렸다. 이제 보이는 행과 위아래
  10행만 그리고 스크롤 위치에 맞춰 바꾼다(`media/main.js` `renderRows`). 행 높이는 결과를 비울 때마다 다시
  재므로 글꼴 크기 변경을 따른다. 화면 상한이 없어져 "화면 표시 항목이 일부 생략" 안내를 뺐다. Edge 헤드리스에서
  실제 webview HTML에 3,000파일·60,000건을 보내 비교했다. 마지막 결과까지 그리는 시간은 940ms에서 14ms로
  줄었고 DOM 행은 20,000개에서 23개가 됐다. End·Shift+방향키·클릭 선택, 선택 행 스크롤, 빈 결과 뒤 재검색도
  확인했다.

- **전체 일치 개수 상한**: 결과는 파일 3,000개 × 파일당 500건, 최대 150만 건까지 미리보기와 함께 worker에서
  확장 호스트, webview로 두 번 복사됐다. 새 설정 `vsearch.maxTotalMatches`(기본 20,000, 0은 제한 없음)에 닿으면
  worker가 남은 개수만큼만 찾고 멈추며, 상태 표시줄에 결과 수 상한 도달을 알린다. 모두 바꾸기의 대상 수집은
  이 상한을 쓰지 않으므로 모든 파일을 바꾼다.

- **프로젝트 캐시 형식 v2**: 텍스트를 JSON 안의 JSON으로 저장하고 SHA-256으로 검사하던 v1을 바이너리 형식으로
  바꿨다(`.vshoon/cache/vsearch-v2/*.bin`). 48바이트 머리글(메타데이터, 길이, CRC32), 1KiB 필터, UTF-8 텍스트
  순서다. 시작할 때 이전 `vsearch-v1` 폴더는 백그라운드에서 지운다. 2,000개 파일(원본 23.7MiB)에서 디스크 IO를
  뺀 형식 처리 비용은 쓰기 243→62ms, 읽기 183→28ms, 캐시 크기는 37.0→25.7MiB다. 디스크를 포함한 측정은
  같은 조건에서 실행마다 8배까지 흔들려 비교하지 않았다. 파일별 캐시를 pack 파일 하나로 모으는 방식은 여러 창이
  같은 프로젝트를 열 때의 동시 기록 문제가 있어 하지 않았다.
- **파일 목록을 worker가 보관**: 키 입력마다 최대 2만 개 경로를 복사해 worker로 보냈다. 이제 열거한 목록을 한 번
  보내고 생성은 `filesAdd`, 삭제는 기존 `invalidate`로 고친다. 검색 요청에는 범위·마스크(`WorkspaceScope`)만
  담는다. findFiles를 써야 하는 범위(워크스페이스 밖, 경로가 들어간 마스크, 잘린 목록)는 경로를 그대로 보낸다.
  worker를 다시 만들면 목록을 다시 보낸다.
- **미저장 내용은 바뀐 것만 전송**: 검색마다 모든 미저장 문서의 텍스트를 복사했다. `DirtyTextTracker`가 문서 버전을
  기억해 바뀐 문서만 읽어 보내고, 저장하거나 닫은 문서는 worker에서 지운다.

`npm run test:vsearch` 17개와 기존 매칭 검사 18개가 통과했다. 미저장 내용 테스트 6개는 새 방식의 2개(버전 변경분,
실제 worker의 목록·범위·미저장 내용 검색)로 바꿨고, 바이너리 생략·루트 기준 폴더 판정·전체 일치 상한 테스트를 더했다.
`npm run smoke:java-search`는 v2 캐시 파일을 읽도록 고친 뒤 실제 확장 호스트에서 통과했다(자동 인덱싱,
생성·수정·삭제 즉시 반영, 프로젝트 캐시, 미저장 내용 검색, 팝업). 처음 실행은 smoke가 v1 JSON 형식으로 캐시를
읽어 실패했다. 두 실행의 임시 프로필은 직접 지웠다.
